# 陪伴型 Agent 长期记忆系统设计（DSH / owner-memory）

> 适用对象：DeepSeek Harness（DSH）里工具面全开的陪伴型 agent。
> 记的是**主人的事**，不是 agent 自己的人格养成。
> 版本：draft-1，2026-11-02，对标 DSH 0.2.1-rc.5 + `preset-whalechan-fixed`。
> 代号：`owner-memory`，插件包名暂定 `dsh-owner-memory`，工具前缀 `mem_`。

本文只写设计，不写实现代码。每个决定后面都跟「为什么这么定 / 另一种做法为什么不行」。

## 1. 目标 / 非目标 / 硬约束

### 1.1 目标（G）

| 编号 | 目标 | 可验收的说法 |
|---|---|---|
| G1 | 记主人的事 | 系统能稳定承载九类内容：偏好、约束与红线、约定、关键决策、当前状态、待办、常用路径/命令、踩过的坑与修法、已验证的事实。每类有明确的 `kind` 或 `tags` 落点，不靠自由文本猜 |
| G2 | 每条带时间 | 任意一条记忆都能回答「这话是什么时候的事」：存储层有 `ts`（带时区的 ISO8601），召回与注入的渲染里必须出现日期 |
| G3 | 事实可变、旧值留痕 | 同一事实键的新值自动取代旧值；旧值不删除、可通过 `mem_audit` 查到、可撤销（撤销后旧值重新生效） |
| G4 | 纠正留痕 | 不存在「原地改掉一条旧记忆」的写路径。纠正只能产生新事件并指向被纠正的 id |
| G5 | 常驻注入小 | 每轮注入的 L0 文本 ≤ 1200 中文字符（按字符数计，不是 token），且该上限在代码里是硬断言不是约定 |
| G6 | 按需召回 | 只读召回工具，条数与字数双封顶，每条带 id；返回体里不出现总数、不出现「还有 N 条」这类诱导模型继续要的字样 |
| G7 | 写得进去 | 在 `workspace-write` 文件策略下，不弹授权框就能完成全部写入；真相源文件默认落在工作区内 |
| G8 | 写不丢、不互相覆盖 | 并发写入不丢行、不串行化覆盖；进程崩溃最多丢最后一次未完成的追加，已返回成功的写必然在盘上 |
| G9 | 可审计 | 能回答三个问题：这条为什么被选中/没被选中、哪些快忘了、哪些被取代了 |
| G10 | 轻依赖 | 单机、单人、中文语境；零第三方运行时依赖（Node 内置模块 + 本仓代码） |
| G11 | 可迁移 | 能从现有 loli 四区 markdown 全量导入，条目数可核对，不丢内容，重复执行不产生重复条目 |

### 1.2 非目标（NG）

- **不做人格养成**：没有阶段、信念、立场、好感度、拒绝机制。样本 B 的 `utterance / narration / dream / diary / refusal` 一个都不抄——那套模型的主语是 agent 自己，而本系统的主语永远是主人或主人的项目。
- **不做对话全文归档**：逐轮原话属于会话历史与 compaction 的职责，记忆只存「值得长期持有的陈述」。
- **不做多用户 / 多租户 / 权限模型**；**不做跨机同步**（备份靠文件复制，不做冲突合并）。
- **不做向量检索 / embedding（2026-11-04 实测后修正）**：向量层已实现为实验层（wasm + worker + `vec.bin`），但实测 C 组 0/4、P 题零增益、p95 569ms，**默认关闭**（`vector.enabled=false`）。重开条件见 §15.4；**不做自动总结 agent**（见 §8.4）。

### 1.3 硬约束（C）

| 编号 | 约束 | 来源 |
|---|---|---|
| C1 | agent 自身的 `shell` / `edit` 工具受 `workspace-write` 限制，工作区外写入必然被拒 | 实测：`EPERM: open ...package.json.lock`、`[sandbox: file access denied under workspace-write mode]` |
| C2 | 插件在宿主进程内的 fs 调用**不受**该沙箱限制 | 实测：`whale_memory_add` 能写 `~/.dsh/whale-chan-memory.md` |
| C3 | `persona` section 是 `complete: true`，宿主会丢弃其它 section | `dsh-whale-loli/src/memory.js` 顶部注释；实测「34 条真实系统提示里记忆段出现 0 次」 |
| C4 | Windows 文件系统会给出 `EPERM / EACCES / EBUSY / ENOTEMPTY` 瞬时错误 | 样本 B 的重试表就是为此存在 |
| C5 | 写文件前必须先 `read`（fs-observation-policy），且工具写过之后 mtime 变化会导致 `file changed since it was read` | 实测 |
| C6 | 中文没有空格，不能按空白切词 | 样本 B 为此加了「≥3 字才切二字切片」的补丁 |

## 2. 总体架构：三层

### 2.1 职责边界

| 层 | 名字 | 内容 | 真相源？ | 读路径 | 写路径 | 预算 |
|---|---|---|---|---|---|---|
| L0 | 常驻事实 | 红线、进行中待办、高分事实键的当前值、最近关键决策 | 否，派生自 L1 | 每轮注入提示变量 | 不可直接写，由 L1 重算 | ≤1200 字符 |
| L1 | 事件日志 | 全部写入，只追加 | **是** | 不进上下文 | `mem_fact`/`mem_note`/`mem_fix` 三个写入口 | 无上限（有折叠） |
| L2 | 按需召回 | L1 的检索视图 | 否，派生自 L1 | `mem_recall` 工具调用 | 只读 | ≤4 条 / ≤800 字符 |

三层的分界线是一句话：**L1 决定「是什么」，L0 决定「每轮都要知道的是什么」，L2 决定「这次问话需要知道的是什么」。** L0 和 L2 都可以随时删库重建，删了只影响这一轮的效果，不影响任何事实。

### 2.2 为什么是三层，而不是样本 A 的四区

样本 A 的四区（固定 / 滚动 / 详细 / 归档）是**一个文件里的四段文本**，没有层级语义：
- 「固定」与「滚动」的差别只是会不会被 FIFO 挤掉，不是「每轮要不要进上下文」——结果 16000 字符的全文每轮都注入，预算完全失控。
- 「最近详细区」是滚动区的副本。本机实测该区内容与滚动区逐条重复，且因为 read-modify-write 全量覆盖，已经出现了多条被逗号粘连成一行的损坏（`...已写盘,- R0006 [...]...`）。一个结构如果能被自己的写路径破坏，它就不是结构。

三层把「真相」和「预算」正交开：真相只在 L1，预算只在 L0/L2。改预算不碰数据，改数据不碰预算。

### 2.3 数据流图

```
                               ┌─────────────────────────────────────┐
  主人说话 / agent 判断          │           模型上下文                  │
        │                      │  persona prefix (complete:true)     │
        v                      │    ...人设文本...                    │
  ┌──────────────────────┐      │    {{owner_memory}}  <── L0 注入     │
  │ mem_fact / mem_note  │      │  tool result: mem_recall(...)       │
  │ mem_fix  (三入口一路径) │      │    [m_7f3a | 2026-11-02] ...   <──┼─┐
  └──────────┬───────────┘      └─────────────────────────────────────┘ │
             │ dedup → append 1 line（不持锁，§4.4）                     │
             v                                                         │
  ╔═════════════════╗                                                  │
  ║  L1 事件日志     ║ ← 真相源，只追加，一行一个 JSON                      │
  ║  events.jsonl   ║                                                  │
  ╚════╦════════════╝                                                  │
       ║ derive（启动时 / 写后增量 / sourceHash 不匹配时全量；持锁）         │
       ╠══> state.json   派生：key 当前值 + 取代链 + 状态表 + 固化计数       │
       ╠══> index.json   派生：bigram 倒排 + df 统计                      │
       ╚══> pinned.md    派生：L0 注入原文（人可读，agent 可直读）──┐       │
                                                                │       │
  每轮组装提示词 ──> 读 pinned.md（≤1200 字符）───────────────────┘       │
  模型调用 mem_recall(query) ──> 查 index.json + 评分 ──> 封顶裁剪 ───────┘
```

关键性质：**所有箭头都从 `events.jsonl` 出发向外，没有一条箭头指回去。** 任何「改 state.json 就当改了记忆」的写法都不允许（这条直接继承样本 B 的注释，它是对的）。

## 3. 数据模型

### 3.1 事件 schema

一行一个 JSON，不缩进，不含裸换行（`text` 里的换行写成 `\n`）。

| 字段 | 类型 | 必填 | 含义与取值 |
|---|---|---|---|
| `id` | string | 是 | `m_` + base36(ts 毫秒) + `_` + 4 位随机。全局唯一，生成后不变 |
| `ts` | string | 是 | ISO8601 带时区，如 `2026-11-02T08:15:00+08:00`。本地时钟，不做 NTP 校正 |
| `kind` | enum | 是 | 见 §3.2 |
| `text` | string | 是 | **带时间信息的陈述句**，1–200 字符。写「主人 11 月起改用 pnpm」而不是「改用 pnpm」 |
| `key` | string | `kind=fact` 必填 | 事实键，`对象.方面` 形式。见 §3.3 |
| `tags` | string[] | 否 | 0–5 个。约定词表：`偏好 约定 红线 决策 状态 待办 路径 命令 坑 验证` |
| `weight` | 1–5 | 否 | 重要度，默认 2。5 保留给红线与明确的「记住」 |
| `refs` | string[] | `revise/retract/close` 必填 | 指向已存在的事件 id；内部 `supersede` 恰好 2 条、`alias`/`confirm` 恰好 1 条 |
| `aliases` | string[] | 否 | 1–3 条俗称（2026-11-04 新增）。只对 `fact`/`note` 有效；写入侧只生成提案，人审后由 `kind=alias` 事件落盘才参与打分 |
| `aliasQuote` / `ownerQuote` / `clearKey` | string / string / string[] | 否 | 俗称出处原话 / 主人撤销原话（仅 rule 的 retract）/ 显式清空键（仅无回退目标时） |
| `scope` | enum | 否 | `local`（默认，本工作区）/ `global`（跨工作区） |
| `src` | string | 否 | `agent`（默认）/ `user`（主人原话复述）/ `migrate:loli` / `fold` |
| `sess` | string | 是 | 写入时所在会话 id，由宿主提供。carry 规则（§6.4）依赖它；初版漏了这个字段，R6 评审时补上 |
| `pin` | bool | 否 | 请求进入 L0。只是**请求**，最终由 §6.2 的预算仲裁决定 |

示例行（真实格式，原样可入盘）：

```json
{"id":"m_lq8f3a_7c1d","ts":"2026-11-02T08:15:00+08:00","kind":"rule","text":"主人的红线：不许在未经确认的情况下 commit 或 push，plan mode 下一句话同意不算批准。","tags":["红线"],"weight":5,"pin":true}
{"id":"m_lq8f41_2b90","ts":"2026-11-02T08:16:12+08:00","kind":"fact","key":"桌面profile.包管理器","text":"desktop profile 从 2026-11 起用 pnpm 管依赖，不再用 npm。","tags":["约定"],"weight":3}
{"id":"m_lqa02c_51ef","ts":"2026-11-02T09:40:03+08:00","kind":"note","text":"坑：whale_memory_add 写过之后记忆本 mtime 变，edit 会报 file changed since it was read；修法是写完重新 read 一次再 edit。","tags":["坑","验证"],"weight":3}
{"id":"m_lqa1b7_c3aa","ts":"2026-11-02T10:02:41+08:00","kind":"decision","text":"决定记忆真相源放工作区内 .dsh-mem/，不放 ~/.dsh，理由是沙箱与可审计。","tags":["决策"],"refs":["m_lqa02c_51ef"],"weight":4}
{"id":"m_lqd55e_08b2","ts":"2026-11-03T14:21:09+08:00","kind":"fact","key":"桌面profile.包管理器","text":"主人 11-03 改回 npm，因为 pnpm 的 link: 协议在本机 resolve 失败。","tags":["约定"],"weight":3}
{"id":"m_lqd77a_9f04","ts":"2026-11-03T15:10:00+08:00","kind":"revise","text":"更正：whale_memory_add 的 mtime 问题不是写入导致，是宿主每轮重读时的 touch；修法同样是重读。","refs":["m_lqa02c_51ef"],"weight":3}
```

读这六行就能看出全部机制：第 2 行与第 5 行同 `key`，第 5 行**自动取代**第 2 行；第 6 行 `revise` 显式**修正**第 3 行。两者都没有删除任何东西。

### 3.2 kind 取值与触发条件

| kind | 含义 | 触发条件（什么时候该写这一条） | key | refs | 默认半衰期 |
|---|---|---|---|---|---|
| `fact` | 可变事实的当前值 | 主人的属性 / 环境 / 配置 / 已验证结论，且**能起一个不含值的键** | 必填 | — | 180 天 |
| `rule` | 约束与红线 | 主人说「不许」「必须」「以后都」；或 plan-mode 这类硬约束 | — | — | 不衰减 |
| `decision` | 关键决策 | 在两种以上方案里选了一种，且以后会被问「为什么是这样」 | — | 可选，指向依据 | 365 天 |
| `todo` | 待办 | 明确承诺要做、尚未做完的事 | — | — | 30 天 |
| `note` | 经验 / 坑 / 路径 / 命令 | 其余值得记但起不出稳定键的 | — | — | 90 天 |
| `revise` | 修正 | **旧条目当时就记错了**（记录错误、理解错误） | — | 必填 | 跟随 kind 默认 |
| `retract` | 撤销 | 整条作废且无替代（如：误记了别人的事） | — | 必填 | — |
| `close` | 关闭待办 | `todo` 完成或放弃 | — | 必填 | — |
| `supersede` | 内部：取代 | 仅迁移代码写，`refs=[旧,新]`，把「被 retracted 的历史条目」改判为「被取代」 | — | 恰好 2 条 | — |
| `alias` | 内部：俗称 | 人审后由 apply 脚本写，给已有条目挂俗称；`src=review` | — | 恰好 1 条 | — |
| `confirm` | 内部：确认 | 去重命中时写一条，derive 累计 `confirmCount` / `lastSeenAt` | — | 恰好 1 条 | — |

**为什么把 `close` 单列，而不是用 `revise` 表示待办完成**：`revise` 的语义是「当初就错了」，用它关待办会污染审计——体检时无法区分「我记错了一个待办」和「这个待办做完了」。而用 `fact` + 状态键表示待办（如 `待办.迁移记忆.状态`）也不行：待办天生是一串事件而不是一个值，键会爆炸成 `待办.<任意 slug>.状态`，违反 §3.3 的「键里不许含具体值」。

**为什么没有 `update` / `edit` 这种 kind**：那会诱导模型以为存在原地改写。所有「变了」都通过新增一条同键 `fact` 表达。

### 3.3 事实键规范

形式：`<对象>.<方面>`，两段，中间一个半角点。归一化规则：全角点转半角、去首尾空格、ASCII 部分转小写、中文不转换。

**铁律：键里不许出现具体的值。** 这条直接抄样本 C，它的论证是对的：若键写成 `主人.身高180`，身高一变键也变，新旧两条永远碰不上，取代机制彻底失效。

| 反例 | 问题 | 正确写法 |
|---|---|---|
| `主人.身高180` | 键里含值 | `主人.身高` |
| `项目.用pnpm` | 键里含值 | `桌面profile.包管理器` |
| `主人` | 没有方面，整个对象会被一条覆盖 | `主人.作息` |
| `偏好` | 没有对象，不同对象互相覆盖 | `主人.编辑器偏好` |
| `主人.喜欢的东西` | 方面太粗，一个键装不下多个事实 | 拆成 `主人.编辑器偏好` / `主人.咖啡偏好` |
| `dsh.0.2.1.路径` | 含版本号（版本会变） | `dsh.安装路径` |
| `主人.今天的心情` | 含时间词，键天天变 | 不该用 `fact`，用 `note` |

键不存在时如何起：对象优先用已有对象（`mem_audit(what="keys")` 可列出），方面用名词不用动词短语。起不出来就别用 `fact`，用 `note`——**宁可降级成无键条目，也不要造一个坏键**。坏键造成的伤害（取代链断裂、同键多个 active）比没有键大得多。

### 3.4 supersede（取代）与 revise（修正）的区别

这是整个数据模型里最容易混的地方，必须分清。

| | supersede 取代 | revise 修正 |
|---|---|---|
| 语义 | 旧值**当时是对的**，世界变了 | 旧值**当时就是错的**，我记错了 |
| 触发方式 | **隐式**：写入同 `key` 的新 `fact` 时由 derive 自动判定 | **显式**：`kind=revise` + `refs=[旧id]` |
| 旧条目状态 | `superseded`，`supersededBy=<新id>` | `revised`，`revisedBy=<新id>` |
| 旧条目召回权重 | ×0.02 | ×0.02 |
| 旧条目进 L0 | 否 | 否 |
| 历史可查 | 是，`mem_audit(what="key", key=...)` 出完整时间线 | 是，`mem_audit(what="id", id=...)` 出引用链 |
| 可撤销 | 是：对新条目 `retract`，旧条目自动回到 `active` | 是：对 revise 条目 `retract` |
| 典型句子 | 「主人改用 npm 了」 | 「我之前记错了，那个报错不是写入导致的」 |

**为什么取代要做成隐式**：如果要求模型每次都显式写 `supersedes`，它就必须先召回拿到旧 id 再写——两步，而模型经常只做第一步。键相同就是取代，这个规则不需要模型记住任何 id。

**为什么修正必须显式**：修正没有键可依（被修正的往往是 `note`），而且「我错了」这件事本身需要留痕给审计看。隐式推断「这句和那句矛盾」需要语义理解，不可靠。

**样本 B 的缺陷在这里被修掉**：它把 `revise` 的引用计入被引用方的加权，导致被推翻的原句排名反而更高。本设计规定——

> **引用加权只加给引用者，不加给被引用者。**
> 并且 `revise` / `retract` 是**否定性引用**：不仅不加分，还直接把被引用条目打到 `revised` / `retracted` 状态，penalty 乘子 0.02 / 0.0。
> 只有 `decision` / `note` 对条目的引用算**肯定性引用**（「这条是我做决定的依据」），才给被引用方加分。

**`revise` 打到「当前值」上时，`byKey` 怎么走**（2026-11-02 P2a 补定，实现时发现的空档）。`retract` 的规则已经明确（§12 A9：撤掉 v3，`byKey` 回退到 v2 且 v2 回到 `active`），但 `revise` 只写了「旧条目状态变 `revised`」，没写键指向哪。不定义就会出现这个后果：`byKey[key]` 仍指着一条 `revised` 的条目，而 L0 正是按 `byKey` 取「当前值」——**于是一个已经被判定为记错的值会被当作现状每轮注入**，只是召回时被 0.02 压住。所以定死：

- `revise` / `retract` / `close` 命中某键的**当前值**时，三者一律让 `byKey` **回退到该键上一条未被否定（非 `superseded/revised/retracted/closed`）的 fact**；没有这样的旧值就**删除该键**。三者语义只有状态名不同，键的处置完全一致——没必要为 `revise` 单独发明一套。
- 正确的用法仍然是「要改值就写一条同键的新 `fact`」：`revise` 表达的是「当初记错了」，不是「值变了」。前者的补偿是新事实，后者靠取代。这在 §5.3 的是非问句里已经被区分过一次，这里是它在数据层的对应。
- 验收就挂在 A9 旁边，见 §12 A9b。

## 4. 文件布局

### 4.1 目录树

```
图例：★ 真相源 ○ 可删除并重建的派生品 △ 只写不读的审计流 ⚠ 证据 ⚙ 运行时

<workspace>/.dsh-mem/        ← 默认根。在工作区内，所以 agent 自己能读
├── events.jsonl             ★ 真相源。只追加，一行一事件
├── events.jsonl.meta        ★ 尾部校验（行数 / 末行 id / sha256 前 16）
├── state.json               ○ key→当前值、取代链、状态表、固化计数、migratedIds
├── index.json               ○ bigram 倒排表 + df 统计
├── pinned.md                ○ L0 注入原文，人可读
├── health.json              ○ 最近一次体检结果
├── recall-log.jsonl         △ 召回回执，只追加，保留最近 200 次
├── .gitignore               ⚙ 内容是 `*`，自忽略，见 §9.4（R7）
├── .lock/                   ⚙ 锁目录（mkdir 原子性），内含 owner.json{pid,ts,op}
├── corrupt/events-<ts>.jsonl  ⚠ 解析失败的原始行，原样留证，永不自动删
└── archive/
    ├── 2026-Q4.jsonl        ★ 折叠出去的事件（仍是真相的一部分）
    └── snapshot-<ts>.jsonl  ⚠ 折叠前的 events.jsonl 完整副本

~/.dsh/owner-memory/         ← 可选的 global scope 根，结构同上
```

**判定规则**：`rm state.json index.json pinned.md health.json` 之后，系统必须能从 `events.jsonl` + `archive/*.jsonl` 完全重建，且重建结果逐字节一致（见 §12 A1）。做不到就是设计被破坏了。

### 4.2 为什么真相源在工作区内

C2 说明插件写 `~/.dsh` 其实是能写的，那为什么不放那儿？三个理由：**可审计**（主人用编辑器、`findstr` 直接看，不用先想起路径）；**agent 自己能读**（出问题时用 `read` 看 `events.jsonl` 末尾自诊断，不需提权——样本 A 的记忆本在工作区外，看一眼都要弹授权框）；**跟项目走**（陪伴型 agent 的大部分记忆是路径、命令、坑，换工作区时不该跟过去）。

代价：跨工作区的长期事实（作息、称呼、红线）会被困在某个工作区。解法是 `scope: global` 写到 `~/.dsh/owner-memory/`，由插件进程直接写（C2 允许）。**global 根只收 `rule` 和 `weight>=4` 的 `fact`**，其余一律 local——否则全局库会变成第二个大杂烩。

**另一种做法为什么不行**：只用 `~/.dsh` 一个全局根（样本 A 的做法）。实际结果是本机实测出的那样：agent 读得到写不进（需求 7 直接否掉），而且「上个项目的坑」会持续污染新项目的召回。

### 4.3 单写者与锁

- **进程内**：插件内部一个串行队列（async mutex），所有写操作排队。同一进程内不存在并发写。
- **跨进程**（多个 DSH 窗口打开同一工作区）：`.lock/` 目录，用 `mkdir` 的原子性做互斥，内写 `owner.json{pid, ts, op, token}`。获取失败时退避重试 `0 / 20 / 60 / 120 / 240 ms` 五档（抄样本 B 的重试表，它是为 Windows 的 `EPERM/EACCES/EBUSY/ENOTEMPTY` 调出来的，C4）。锁的 `ts` 超过 15 秒视为陈旧，可强行抢占并在 `health.json` 记一次 `lock_stolen`——15 秒远大于任何正常写操作（追加一行是毫秒级），能走到这一步说明持锁进程已经死了。
- **重试预算 = 档位 × 轮数，不是「五档就算完」**（2026-11-02 P1 实测补充）。五档走完只有 440 ms，这在一对进程争抢时够用，但实测 A3（两个子进程各写 100 条、连跑 20 轮）在机器忙时会出现个别轮次撞 `E_LOCK_TIMEOUT`——40 个短命子进程排队，440 ms 塞不下。所以定：**五档是一轮的退避表，获取锁时循环走这张表直到 `lockMaxWaitMs`（默认 5000 ms；2026-11-04 由 2000 上调）或成功**；超过才抛 `E_LOCK_TIMEOUT`。同时保留**等待者交接**：持锁者在释放前若看到 `.lock-waiter-*` 存活标记，先让出 `handoffMs`（默认 60 ms）再走，避免同一进程连续抢回锁把别人饿死。`lockMaxWaitMs` 必须远小于 `staleLockMs`（5000 ≪ 15000），否则正常排队会被误判成持锁者已死而被抢占。**上调依据**：A3b（40 个短命子进程并发写）在满负载下会以「锁等待约 2017 ms」超时，2026-11-04 一天内复现 5–6 次，单跑必过。
- **`.lock-claim`（抢占用的暂存目录）与主锁同一套语义**：内含 `{pid, ts, op, token}`，超过 15 秒同样可被接替。没有这条，进程在抢占期间被 kill 会留下一个永远抢不到的 claim 目录，此后所有写入永久 `E_LOCK_TIMEOUT`——这是实现时踩到过的真实死锁，见 A15b。
- **读租约文件的竞态按「读不到」处理**（2026-11-02 P4 实测补充）。Windows 上一个正被别的进程写入或删除的 `.lock-waiter-*` / `owner.json`，`readFileSync` / `statSync` 抛的是 `EPERM` / `EACCES` / `EBUSY`，**不是 `ENOENT`**。如果只吞 `ENOENT`，这类并发读竞态会直接把整个写入打成失败——实测在满负载 A3b 里漏出来过一次（报「waiter 读取 EPERM」）。规矩：锁层的所有租约读取，`ENOENT` / `EPERM` / `EACCES` / `EBUSY` / JSON 解析失败一律当作「这个租约现在读不到」，最坏后果只是少让出一次 handoff 或本轮跳过抢占，绝不能升级成写入失败。
- **锁只保护派生品的重算与折叠，不保护追加本身**。

### 4.4 为什么追加不需要锁

`events.jsonl` 的写是 `appendFileSync(path, line + '\n')`，单行且远小于 4KB。POSIX 与 NTFS 对 O_APPEND 的单次小写入都提供原子性，不会交错。更重要的是：**追加天然不会覆盖别人的内容**。

这正是对样本 A 主要缺陷的回答。样本 A 的每次写是 read-modify-write 全量 `writeFileSync`，无锁，于是 idle 归档整理与 `whale_memory_add` 互相覆盖——本机记忆本的「最近详细区」里那些被逗号粘成一行的条目就是这个 bug 的现场。只追加从结构上消灭了这类 bug：**没有 read 就没有 stale read，没有全量写就没有覆盖**。

### 4.5 原子写与损坏留证

- **派生品**（`state.json` / `index.json` / `pinned.md` / `health.json`）：写 `*.tmp.<pid>` → `fsync` → `rename` 覆盖。`rename` 在同卷内是原子的，读者要么看到旧的要么看到新的，不会看到半截。失败按 §4.3 的五档重试。
- **坏行处理**：解析 `events.jsonl` 遇到 JSON 语法错误或 schema 不合法的行时，跳过该行并继续解析后续行（**不中断**：一行坏了不能让整个记忆系统瘫痪），同时原样复制到 `corrupt/events-<ts>.jsonl`（连同行号），并在 `health.json` 记 `corruptLines`（2026-11-05 起记的是「本次扫描实际坏行数」，坏行清掉即归零；历史峰值另存 `corruptLinesEver`，见 §16.1）。
- **绝不重写 `events.jsonl` 来「清理」坏行**。重写就破坏了只追加保证，而只追加保证正是我们能信任这个文件的全部原因。坏行留在原地，代价只是每次解析多跳几行。样本 B 把坏文件整个改名 `.corrupt.<ts>` 的做法在这里不适用：它是整文件级别的，而我们希望单行损坏不影响其余 99.99% 的数据。
- **耐久性分三档，不是所有文件都 fsync**（2026-11-02 P1 实测补充）。此前实现把一切写在盘上的东西都走 `tmp → fsync → rename`，结果 A3b（40 个短命进程洪峰）里每个进程都串行 fsync 一遍租约和 `events.jsonl.meta`，2 秒预算被磁盘同步吃光。分档：
  - **必须 fsync**：`events.jsonl` 的追加、以及派生品（`state.json` / `pinned.md` / `health.json`）的替换——这些丢了就是数据丢了。
  - **不 fsync，普通写**：`.lock/owner.json`、`.lock-claim/owner.json`、`.lock-waiter-*` 这些**运行期协调元数据**。它们丢了只会让人多等一次或误判一次陈旧，代价是毫秒级；用 fsync 换这点确定性不划算，而且会把并发写入串行化。
  - **可复用，每次写前查新鲜度**：`events.jsonl.meta`。它完全由 `events.jsonl` 计算得出（§4.1 的 ★ 应理解为「关键」而非「真相」），洪峰里较早持锁的进程往往已经把后来的追加一并纳入，后到的进程查一次新鲜度就能直接复用，不必重复 fsync。

## 5. 写入 API

### 5.1 工具清单

五个工具（三写两读），全部在宿主进程内执行 fs（C2，所以不触发沙箱提权）。

| 工具 | 读写 | 作用 |
|---|---|---|
| `mem_fact` | 写 | 带键的事实，**键值覆盖语义** |
| `mem_note` | 写 | 无键追加：`note` / `rule` / `decision` / `todo` |
| `mem_fix` | 写 | 纠正类：`revise` / `retract` / `close`，必带 `refs` |
| `mem_recall` | 读 | 按需召回 |
| `mem_audit` | 读 | 审计：召回回执 / 体检 / 键时间线 / id 引用链 / 开关状态 |

第六个工具 `mem_migrate`（loli 四区 md 一次性导入）**已于 2026-11-03 删除**：本机实际迁移是手工筛的，`events.jsonl` 里 `src=migrate:loli` 的事件零条，工具从未被调用；留着它等于在工具表里敞一扇没人走的门。删掉的范围是工具注册 + `src/migrate.js`，守卫它的 A12/A13 用例一并撤除，§10 只作历史记录保留。

三个写工具**共用同一条追加路径**：都归一化 → 查重 → `appendFileSync` 一行 → 持锁重算派生品。它们不是三种写法，是同一种写法的三个入口。

### 5.2 为什么是三个写入口（R1：部分接受）

初版设计只留一个 `mem_write`，论据是「事实键覆盖不是一种写操作，它是 derive 的派生结论，所以写入层面没有区别」。这个论据在**数据模型层面**仍然成立，但它回答的是错误的问题——工具签名要服务的是模型的选择准确率，不是数据模型的优雅。评审 R1 指出的代价是对的：

> 「该写 fact 却写 note」会让取代机制**整体失效**。

这是一个**不对称错误**。写错成 `note` 不会报错、不会告警，条目照样落盘、照样能被召回，表面上一切正常；但这个事实从此没有键，永远不会被新值取代，三个月后库里躺着五条互相矛盾的「主人用 X 包管理器」，全是 `active`。而反向错误（本该 note 却写成 fact）会在 `E_BAD_KEY` 处当场被拒。**一侧静默腐蚀、一侧当场报错，不能用同一个入口赌模型选对。** 所以接受拆分。

但拆成 R1 要求的两个不够，要拆成三个。理由是 R1 自己的论据：条件必填对模型不友好。如果只拆 `mem_fact` / `mem_note`，那 `revise` / `retract` / `close` 只能塞进 `mem_note`，而它们的 `refs` 是必填——`oneOf` 又回来了，只是从 `key` 换成了 `refs`。同一条论据既然能证明该把 `fact` 拆出去，就同样能证明该把纠正类拆出去。三个入口之后，**每个工具的必填项都是无条件的**：`mem_fact` 恒要 `key`，`mem_fix` 恒要 `refs`，`mem_note` 两个都不要。JSON Schema 里一个 `oneOf` 都不剩。

### 5.3 模型怎么判断该用哪个（R1 的第三问）

R1 给的判据是「能起出不含值的键就 fact，起不出就 note」。**这个判据对模型太难**，因为它要求模型先完成一次构造任务（造键），再根据构造是否成功做分类决策——模型几乎总能硬造出一个键来，于是判据退化成「永远选 fact」。

替代判据是一个**是非问句**，不需要构造任何东西：

> **「这句话以后会不会出现一个新版本，让现在这句变成假的？」**
> 会 → `mem_fact`。不会 → `mem_note`。

「主人用 npm」会变假（他可能改用 pnpm）→ fact。「2026-11-02 踩过一个坑：edit 报 file changed」永远不会变假（那天确实踩了）→ note。红线「不许未确认就 push」理论上会变，但变的时候是**撤销**而不是取代，走 `mem_fix` → 所以是 note 家族的 `rule`。

这个判据的好处是它和取代语义**同构**：会变假 = 需要被取代 = 需要键。模型答对这个问句，键就一定起得出来；答错了，`E_BAD_KEY` 会把它弹回来。

三层防护，缺一不可：

| 层 | 机制 | 性质 |
|---|---|---|
| 1 | 工具描述里写死上面的问句，各附 3 个正例 3 个反例 | 事前 |
| 2 | `mem_fact` 的 `E_BAD_KEY` 校验（§3.3 反例表） | 当场拒绝 |
| 3a | `mem_note` 的**键覆盖检查**：文本里同时出现某个**已有 key** 的「对象」段与「方面」段 → 仍然写入，但返回 `warnings: ["这句像 X.Y 这个已有事实键的新值，若是请改用 mem_fact(key='X.Y')；原条已写入 m_xxx，可用 mem_fix(op='retract') 撤销"]` | 实时，不阻断 |
| 3b | 每日体检的**「疑似该用 fact」清单**（§9.2）：扫全部 `note`，凡文本命中任一已有 key 的「方面」段的，列出来交给人回看 | 事后，可审计 |

**第 3 层为什么拆成 3a/3b（R10：部分接受）。** 初版的第 3 层是正则语义嗅探（匹配「X 的 Y 是/为 Z」这类句式）。评审 R10 说它召回率不到 30%、是心理安慰——**这个判断成立**。中文表述千变万化，「主人现在爱用 npm 了」「包管理器换成 npm 了」「依赖都交给 pnpm 了」三句话说的是同一件事，没有一句命中那个句式。一个三成召回率的检查会制造「我有防护」的错觉，比没有更危险。所以**正则句式嗅探整个删掉，不再作为主判据**。

R10 给了两个替代选项，我两个都不单独采纳：

- **(a) 只做每日体检**：对的方向，但只有它不够。体检是次日才看的异步信号，而「该用 fact 却用了 note」的伤害是**从写入那一刻就开始累积**的——这个事实从此没有键，当天就可能被召回好几次，而且主人看到体检清单时已经要回溯一整天的条目。能在写入当场零成本发现的，不该推迟一天。
- **(b) 宽松匹配（已有 key 的方面段 + 一个此前未在同 kind 条目里出现过的 token）**：后半个条件在一个**只追加、永不删除**的库里几乎恒真——任何一条新 `note` 只要措辞略有不同，就几乎必定含有某个首次出现的 token。这等于让判据退化成「只要命中方面段就报」，但又因为多了一个看起来很严谨的条件而掩盖了这一点。它不会比 (a) 更准，只会让 warning 变成固定噪声，而固定噪声会被模型学会忽略。

最终做法是 **(a) 为主，外加一个比 (b) 更强的实时信号**。3a 的关键区别在于：它**不猜语义**，只做一次确定性的子串包含检查，比对的是 `state.byKey` 里一个有限且已知的键集合。它不声称能抓住改写句式——抓不住的全部交给 3b。两者的分工是诚实的：

| | 3a 实时 | 3b 体检 |
|---|---|---|
| 判据 | 对象段 **且** 方面段都出现 | 方面段出现即可（更宽） |
| 误报 | 低（两段同时出现基本就是在说那个键） | 高，但有人看、可忽略 |
| 漏报 | 高（换说法就漏） | 中 |
| 代价 | 一次集合查找，O(键数) | 每日一次全表扫描 |

3a 与 3b 都**不阻断**。理由和 §5.4 的 dedup 一致：为一个假阳性丢掉一条真记忆是不可逆的，多一行 warning 不是。验收用例 A23（3a）与 A23b（3b）。

### 5.4 写入去重（R4：部分接受）

评审 R4 的观察是实测出来的：本机 loli 记忆本十几轮里写了 3 条内容高度重复的「沙箱写不进 .dsh」摘要。只追加 + 模型每轮都想记点什么 = 事件流必然膨胀，而膨胀会同时伤害召回（同一件事占掉多个名额）和折叠（阈值提前触发）。接受加 dedup。

**但不接受「≥0.85 一律阻断」这一种处理。** R4 自己说 0.85 是拍的。在中文短句的 bigram 集合上，Jaccard 0.85 实际上意味着**近乎逐字相同**——两句话只要有一句多了半个从句，相似度就掉到 0.6 上下。所以单一阈值会落进两难：定高了（0.85）只能拦住逐字复读，拦不住真正的同义膨胀；定低了（0.6）就会误杀。

误杀的代价是不可逆的。看这组真实例子：

| 旧条目 | 新条目 | 严格 Jaccard（实测） | 覆盖率口径（实测） | 阻断的后果 |
|---|---|---|---|---|
| 沙箱写不进 `.dsh`，shell 和 edit 都被拒 | 沙箱写不进 `.dsh`，shell 和 edit 都被拒 | 1.0000 | 1.0000 | 正确 |
| 沙箱写不进 `.dsh`，shell 和 edit 都被拒 | 沙箱写不进 `.dsh`，但带 `danger-full-access` 提权重试能写 | **0.3125** | **0.5556** | **灾难**：丢掉的正是「修法」，而修法才是这条记忆的价值 |

**上一版这里写「~0.6」是我拍错了**（2026-11-02 P5 实测更正）。真实数字是：严格 Jaccard 只有 **0.3125**，而「交集 ÷ 较小集合大小」（覆盖率/containment）是 **0.5556**。这解释了两件事：为什么单靠 Jaccard 拦不住真正的复读（多一个从句就把并集撑大），也说明警告带必须换口径，否则这条最该提醒的例子会被判成「无关」。

所以定两个口径，各管一段：

- **阻断**用**严格 Jaccard ≥ 0.85**。它衡量的是「两句话整体是不是同一句」，宁严不宽——阻断是不可逆的。
- **提示带**用**有效相似度 = max(严格 Jaccard, 交集 ÷ 较小集合大小) ≥ 0.55**。覆盖率对称（交换两句话结果不变），对「新写的比旧的多了半句」这类补充/更正敏感，正是提示带要抓的东西。

所以改成**双阈值 + 两套口径**：

| 相似度 | 处理 | 返回 |
|---|---|---|
| 严格 Jaccard ≥ 0.85 | **阻断**，不写入 | `{duplicate: true, id: <首次的 id>, ts: <首次时间>, message: "这条已经记过了（m_xxx，2026-11-02）"}` |
| 有效相似度 0.55 – 0.85 | **写入**，附提示 | `{id, warnings: ["与 m_xxx 相似（0.56），若是更正请改用 mem_fix(op='revise')，若是补充可忽略"]}` |
| 有效相似度 < 0.55 | 正常写入 | — |

候选集限定为**同 kind、近 7 天**（R4 的限定，接受）——跨 kind 比较没有意义（一条 `rule` 和一条 `note` 文本像不代表重复），超过 7 天的重复往往是「这事又发生了一次」，那是信号不是噪声。

**重复不是无事发生，是一次确认。** 被 0.85 阻断时，**追加一条内部 `kind=confirm` 事件**（`refs=[原条目]`，固定文本模板），derive 时累计成 `state.confirmCount` 与 `lastSeenAt`——2026-11-04 起不再直接改 `state.json`，所以这两个字段可重建（§15.5）。这直接喂给 §8.2 的固化判据：一件事被反复想起来记录，正是它重要的证据。R4 把重复当纯粹的污染，这一点我不同意——**丢掉重复的内容，但不要丢掉「重复发生了」这个事实**。

豁免：`mem_fix` 的三种 op 完全不走 dedup。它们是动作不是陈述，「对同一条连写两次 revise」是合法的（第二次可能在修正第一次的措辞）。`mem_fact` 也不走 dedup——同键重复写就是取代，§3.4 已经处理了。**dedup 只作用于 `mem_note` 家族**，与 R4 的要求一致。

### 5.5 三个写工具的签名

```
COMMON = tags?: string[], weight?: 1..5, scope?: "local"|"global", pin?: boolean

mem_fact(key: string,  // 必填，"对象.方面"，§3.3 规范
         text: string, // 1-200 字符，带时间信息的陈述句
         aliases?: string[],   // 可选，俗称（1-3 条）；只生成提案，不直接生效
         aliasQuote?: string,  // 可选，俗称的出处原话
         COMMON) -> { id, status:"written", superseded?: string[], warnings?: string[] }

mem_note(kind: "note"|"rule"|"decision"|"todo",   // 必填，无默认值
         text: string,
         replaces?: string[],  // 可选，被本条取代的旧条目（同 kind、不含 fact、目标须 active）
         aliases?: string[],
         aliasQuote?: string,
         symptom?: string[],   // 可选，1-2 个症状词（每个 2-8 字），仅 tags 含「坑」的 note
         ask?: string[],       // 可选，1-3 句用户口吻问法（每句 6-40 字），仅 tags 含「坑」的 note
         COMMON) -> { id, status:"written", warnings?: string[] }
                   | { duplicate: true, id, ts, message }   // 被 §5.4 阻断

mem_fix(op:   "revise"|"retract"|"close",   // 必填
        refs: string[],                     // 必填，1-3 个已存在的 id
        text: string,                       // revise 必填；retract/close 可为理由
        ownerQuote?: string,                // retract 命中 rule 时必填（主人原话 ≤200 字）
        clearKey?: string[]                 // 会让键失去当前值时必填
       ) -> { id, status:"written", affected: string[], restored?: string[] }
```

`kind` 在 `mem_note` 里**没有默认值**，必须显式给。给了默认值（比如 `note`）模型就会永远用默认值，`rule` / `decision` / `todo` 形同虚设，而这三类恰恰是 L0 常驻段的全部来源。

错误语义（全部是**拒绝写入**，不落盘）：

| 错误码 | 条件 | 返回文案要点 |
|---|---|---|
| `E_BAD_KEY` | `mem_fact` 的键不含点 / 超过两段 / 含明显数值 | 指出哪一段像值 + 最接近的已有键 3 个 |
| `E_REF_NOT_FOUND` | `mem_fix` 的 `refs` 在事件流中不存在 | 列出不存在的 id。**写前必须校验**（抄样本 B） |
| `E_REF_KIND` | `op=close` 的 refs 指向的不是 `todo` | 说明 close 只能关待办 |
| `E_TEXT_TOO_LONG` | `text` > 200 字符 | 要求拆成多条，不自动截断 |
| `E_DISABLED` | 工作区开关关闭（§11.4） | 说明如何打开 |
| `E_LOCK_TIMEOUT` | 循环走完五档退避表直到 `lockMaxWaitMs`（默认 5000 ms）仍拿不到锁 | 报 `.lock/owner.json` 里的 pid 和 op |

注意表里**没有** `E_KIND_REQUIRES_KEY` 和 `E_KIND_REQUIRES_REFS` 了——拆分之后这两种错误在 schema 层就不可能构造出来，这正是 R1 想要的收益。

**为什么 `E_TEXT_TOO_LONG` 不自动截断**：截断会产生半句话，半句话比没有更糟（它看起来像一条有效记忆）。宁可让模型重写。

### 5.6 写入伪代码

三个入口都收敛到同一个 `append_event`，差别只在前置校验和 dedup 开关：

```
mem_fact(a) = append_event({kind:"fact", ...a}, dedup=false)   # 同键即取代，不需要 dedup
mem_note(a) = append_event(a,                   dedup=true)    # 唯一走 dedup 的入口
mem_fix(a)  = append_event({kind:a.op, ...a},   dedup=false)   # 动作不是陈述

function append_event(args, dedup):
    assert_enabled()                            # E_DISABLED
    validate_shape(args)                        # E_BAD_KEY / E_TEXT_TOO_LONG（无条件必填，无 oneOf）
    key = normalize_key(args.key); text = collapse_newlines(trim(args.text)); ts = now_iso_tz()

    if args.kind in {revise, retract, close}:   # 派生品读即可，不必持锁
        for r in args.refs:
            if r not in load_state().byId: raise E_REF_NOT_FOUND(r)
            if args.kind == close and byId[r].kind != "todo": raise E_REF_KIND(r)

    if dedup:                                   # §5.4，仅 mem_note
        cands = index.byKind[args.kind] ∩ index.since(now - 7d)
        best  = argmax(cands, c => effective(text, c.text))   # effective = max(Jaccard, 覆盖率)
        if jaccard(best.text, text) >= 0.85:    # 阻断只认严格 Jaccard
            with lock: append_event({kind:'confirm', refs:[best.id], text:'确认：<id> 再次被想起'})
            return { duplicate: true, id: best.id, ts: best.ts, message: ... }
        if effective(best.text, text) >= 0.55: warnings += near_duplicate_hint(best)
    if args.kind in {note, rule, decision, todo}:
        warnings += fact_smell_check(text)      # §5.3 第 3 层，不阻断

    event = { id: gen_id(ts), ts, sess: host.sessionId, ...args, key, text }
    line  = JSON.stringify(event); assert "\n" not in line
    appendFileSync(events_path(args.scope), line + "\n")   # 不持锁：见 §4.4

    with lock(timeout=five_step_backoff):       # 只锁派生品重算
        st = derive_incremental(event)
        atomic_write(state.json, st); atomic_write(index.json, update_index(event))
        atomic_write(pinned.md, render_L0(st))  # 见 §6
    return { id, status: "written", warnings: warnings + key_smell_check(key),
             superseded: st.lastSuperseded,     # mem_fact
             affected: st.lastAffected, restored: st.lastRestored }   # mem_fix

function derive_incremental(e):
    st = load_state(); st.byId[e.id] = { ...e, status: "active" }
    case e.kind:
      fact:    prev = st.byKey[e.key]                    # 隐式取代
               if prev is active: mark(prev, "superseded", by=e.id)
               st.byKey[e.key] = e.id; st.confirmCount[e.key] += 1   # §8.2
      revise:  for r in e.refs: mark(r, "revised",   by=e.id)
      close:   for r in e.refs: mark(r, "closed",    by=e.id)
      retract: for r in e.refs:
                   mark(r, "retracted", by=e.id)
                   if r.supersededBy: revive(find_superseded_by(r))  # 旧值复活
    st.sourceHash = tail_hash(events.jsonl)     # 行数 + 末行 id + sha256 前 16
    return st
```

注意顺序：**先追加后重算**。如果在重算阶段崩溃，事件已经在盘上，下次启动时 `sourceHash` 不匹配触发全量 derive，自动修复。反过来（先算后写）则会产生「state 里有、events 里没有」的幽灵条目，不可恢复。

### 6.2 上限怎么算

总预算 1200 中文字符（G5 的硬断言）。分段配额**合计恰好 1200**，此前「另留 10% 余量」的说法与下表自相矛盾（300+280+340+120+160 恰好等于 1200，没有余量），现改为把固定开销显式列成一段（旧版这里写的 300+300+400+150+50 是定稿前的数，与表和对齐后的 `LIMITS` 不符，已改正；2026-11-04 又按实测把红线 260→300、事实 380→340）：

| 段 | 条数上限 | 字符上限 | 溢出时 |
|---|---|---|---|
| 红线 `rule` | 6 | 300 | 按 `weight` 降序、同权按 `ts` 降序取前 6；**溢出部分转 L2 强制通道**（§6.6） |
| 在办 `todo`（status=active） | 5 | 280 | 按 `ts` 倒序保留最近的 |
| 事实 `fact`（按下面的 L0 独立选择器） | 8 | 340 | 低分先出局 |
| 决策 `decision` | 3 | 120 | 只留最近的 |
| 固定开销（段标题 + 日期 + id + 尾注） | — | 160 | — |

保障顺序：**红线 > 在办 > 事实 > 决策**。单条超长时截到 **32 字符**加 `…` 与 `(m_xxxxxxxx)`。**2026-11-04 实测更正**：渲染一行实际是 `[标签] YY-MM-DD 正文…(id)`——正文 32 + 前缀 13 + id 括号 17 ≈ 62 字符，不是旧版算的 42。按旧算法「6 条约 252」严重低估，5 条实测就到 305（`[红线] 2026-11-04 ` 前缀 16 字符 × 5 全被漏算），于是 `rules_overflow` 常年为 true、L0 尾注每轮喊「红线已截断」。现在两处一起改：日期压成 `YY-MM-DD`（省 2 字符/行，年份仍保留）、红线段配额 260→300、事实段 380→340。5 条红线约 295 字符，落在 300 内；6 条全满要 372，装不下——这正是 §6.3 强制通道存在的理由。截断后 id 仍在，模型想看全文可以召回。

**为什么是 1200 字符而不是样本 A 的 16000**：16000 字符的记忆每轮都在，占的是每一次模型调用的钱和注意力，而其中绝大部分与当前这句话无关。1200 的量级下，L0 只承担「不知道会出事」的内容，剩下的交给 L2 按需取。

**事实段用独立选择器，不套 §7 公式（R11：接受）。** 初版让 L0 的事实段走 §7 的完整评分，R11 指出这是错的，判断成立：`fact` 的半衰期 180 天、`decay` 下限 0.15，一年后所有老事实全贴在下限上，段内排序退化成「谁新谁上」——于是「用了两年的固定偏好」被上周随手记的一条挤出 L0。这恰恰是 L0 最不该发生的事。根因是目标相反：`decay` 服务的是「这次问话该想起什么」，而 L0 要的是「长期稳定的当前值」，把前者的机制套到后者身上，越稳定的事实排名越低。

```
score_L0(fact) = w_imp(weight)              # 0.8 + 0.2 × weight
               + 0.2  if ageDays <= 30      # 新近度微调，只是微调
               + 0.3  if pin == true        # pin 奖励（仍只是请求，§13-4）
# decay 不参与；base/命中/ref_bonus 也不参与——L0 没有 query，谈不上命中

# 确定性兜底排序（R12 复审补充，必须有）：
#   同分时 confirmCount 降序 → ts 升序 → id
# 没有这一条，30 天以外的一堆 weight=2 键会完全同分，8 个名额的取舍
# 取决于 Map 遍历次序 → 同一份库每轮组装出的 L0 可能不同 →
# 提示词前缀抖动 → prompt cache 每轮失效，且行为不可复现。这不是「排序不理想」，
# 是把缓存打穿。confirmCount 恰好是「被反复确认过」的度量，拿它当第一兜底
# 既稳定又符合本选择器的目标；ts 升序让已在 L0 的条目留住，不扰动现有集合；
# id 只是最后兜底保证唯一。
```

R11 还提到 L0 每轮打分是 O(n)。实际上选择器的候选集不是全部 `fact` 事件，而是 `state.byKey` 里每个键的当前值——**每个键至多一条 active**，被取代的根本不在候选里。所以复杂度是 O(键数) 而不是 O(事件数)，且结果可随 `state.json` 一起缓存，只有写入才会使其失效。

`rule` / `todo` / `decision` 三段本来就不走评分（分别按 `weight`、`ts`、`ts` 排序），所以 L0 整段**完全不依赖 §7**。§7 从此只服务 L2。这个切分本身是个改进：两套排序逻辑各自只有一个目标，不用再互相迁就。

**配额指标必须落盘，否则指标是死的（2026-11-03 补，实现与文档同步）。** §6.2 算出的 `rules_overflow` / `rules_truncated_hard` 不只是给人看的数字——尾注（§6.1）和红线强制通道（§6.3）都以它为准，所以渲染完必须写进 `health.json`。落地方式：`storage/files.js` 的 `persistPinnedHealth(root, health)` 只覆盖这两项，走 `updateHealth` 的函数式 patch 合并，其它健康字段原样保留；调用点是 `index.js` 的 `makeProvider`，每次渲染 `{{owner_memory}}` 后立刻落盘，写失败只吞掉、不影响注入。

初版的漏洞值得记下来：`renderPinned(loadState(config), { health: {} })` 传的是临时对象，算完就丢，于是 §9.2 的 `rules_overflow` 在 `health.json` 里永远是默认值 `0`——**实际截断了也报 false**，而尾注同时在喊「红线内容已截断」，两边自相矛盾。回归用例 `test/l0-health-persist.test.js` 守住三件事：截断时写 `true`、恢复成短红线时能**回落** `false`（只升不降的指标等于没用）、落盘不冲掉 `injection_missing` 等其它字段。这些指标各自意味着什么、为 `true` 时该做什么，见 §9.5 的速查表。

### 6.3 红线溢出：L2 强制通道（R2：接受）

初版写的是红线溢出时「不截断、不丢弃，health 报警」。评审 R2 一句话戳穿了：**报警了然后呢？L0 就是爆了。** 报警是写给主人看的异步信号，而违反红线是当场发生的。拿一个异步信号去挡一个同步风险，等于没挡。

改成：红线可以不常驻，但必须有出口。L0 的红线段只放前 6 条（按 `weight` 降序），溢出的红线进入 **L2 强制通道** `mem_recall(kinds=['rule'])`，该通道有三条特殊规则：

- **不设 `score` 阈值**。普通召回低于 1.0 不返回（§7.5），红线通道不适用——漏掉红线的代价与返回一条无关红线的代价不对称。
- **`query` 可为空**，此时按 `weight` 降序 + `ts` 降序返回，相当于「把剩下的红线全念一遍」。
- **条数上限放宽到 12、字符上限放宽到 1200**，且不占普通召回的名额。红线是唯一获得独立预算的类别。

配套两处改动：L0 尾注在有溢出时改成硬指令 `> 另有 N 条红线未常驻；任何写文件/改配置/跑命令之前，必须先 mem_recall(kinds=['rule'])。`；§6.6 触发条件 3 由「查一次」升级为**强制**。

**这里与 G6「返回里不要出现『还有 N 条』」是否矛盾？** 不矛盾，但必须讲清边界。G6 禁止的是 **`mem_recall` 返回体**里的诱导性计数——那里的「还有 N 条」是一个没有下一步动作的钩子，只会让模型反复追加召回。而 L0 尾注的 N 后面**跟着一个确定的、有终点的动作**（调一次红线通道就把 N 条全拿到了，不存在「再来一次还有更多」）。区别在于：前者是开环的诱饵，后者是闭环的指令。`mem_recall` 的返回体依然一个计数字段都没有。

**另一种做法为什么不行**：把 L0 红线段的预算从 300 扩到不设限。那 1200 的硬预算（G5）就被一个类别单方面废掉了，主人写了 40 条红线就等于每轮注入 2000 字符——G5 是硬约束，不能由某个类别自己豁免。

红线段仍然是唯一不参与**评分淘汰**的段（它按 weight 排序而不是按召回分数），但它不再豁免于预算。

**红线超预算时怎么办：截断文本，不抛异常**（2026-11-02 P3 补定，实现时发现的口子）。初版实现让 `renderPinned` 在「红线内容本身就超过 1200」时直接 `assert` 失败——这是错的，理由和三处呼应：

1. L0 是**每轮组装都要跑**的热路径。在那里抛异常等于把会话打死，而文档 §11.2 已经为「L0 静默失效」设过自检，说明我们对这条路径的要求是「可观测地降级」，不是「炸掉」。
2. 「不截断、不丢弃」的初衷是不许**悄悄**丢掉约束；而截断 + `health.rules_overflow` + 尾注里那句硬指令（`mem_recall(kinds=['rule'])`）是**明示**降级，不是悄悄。
3. 第 512 行的论证已经排除了「给红线段扩预算」这条路，剩下的唯一自洽选择就是「截文本、保条数、留出口」。

所以定死：红线与其它段一样走 32 字符截断；**条数不减**（6 条都在，只是变短）；`health.rules_overflow` 为真；尾注换成硬指令。`renderPinned` **不得抛异常**，任何情况下都返回 ≤1200 的字符串。

### 6.4 长期事实不走检索

抄样本 C 的一条设计：L0 里的事实**不占** `mem_recall` 的条数名额，`mem_recall` 的结果也不与 L0 去重后再补位，两边是独立通道。理由：如果 L0 的内容还要和召回结果竞争名额，就会出现「因为红线已经在上下文里，所以这次召回把相关的坑也挤掉了」这种反直觉结果。

### 6.5 换会话的 carry 规则（R6：接受）

初版写的是「上一会话最后 6 条事件原文」。评审 R6 指出：一个工作区会有多个会话，上一会话若是纯写代码的，carry 就把无关内容搬进新会话。这个批评成立，而且还暴露了一个更基础的缺陷——**初版 schema 里根本没有会话 id，「上一会话」这个概念在数据层面压根表达不出来**。§3.1 因此补了 `sess` 字段。

R6 给了两个候选（按「最近一次有实质写入的会话」筛，或按 kind 筛）。**两个都要，不是二选一**，因为它们挡的是不同的东西：

| 筛法 | 挡掉什么 | 单用为什么不够 |
|---|---|---|
| 会话筛：取最近一个写过 `rule`/`decision`/`todo`/`fact` 的 `sess` | 整段纯代码会话 | 该会话里仍然混着大量 `note` 流水账 |
| kind 筛：只取 `rule`/`decision`/`todo`/`fact` | 流水账 `note` | 一个纯代码会话里偶尔写了一条 fact，就会把那个会话的尾巴拖进来 |

最终规则，新会话启动时除 `pinned.md` 外额外带：

- 取最近一个**实质会话**（该 `sess` 下存在 ≥1 条 `rule`/`decision`/`todo`/`fact` 写入）；
- 在该会话内，**只取** `kind ∈ {rule, decision, todo, fact}` 且 `status=active` 的最后 6 条，`text` **原文**，每条 ≤120 字符，按时间正序，带日期和 id；
- 外加全局全部 `status=active` 的 `todo`（上限 5 条，与 L0 的在办段去重）。

`note` 一条都不 carry。理由：`note` 是坑、路径、命令这类**按需查**的内容，它们的正确通道是 L2 召回（§6.6 触发条件 1），不是无条件搬运。搬 note 正是 R6 抱怨的「无关内容」的主要来源。

若找不到任何实质会话（全新工作区），carry 为空——**不退化成「搬最近 6 条」**。宁可空着，也不要把流水账当成上下文。

carry 总量 ≤ 800 字符，且**只在新会话的第 1 轮注入，第 2 轮起撤掉**（第 2 轮起已有会话内上下文，继续带就是重复占预算）。

**「第 1 轮」怎么判定（R12：接受）。** 初版只写了这个行为，没写它靠什么实现——而宿主每轮都重新组装 prompt，插件本身是无状态的，「这是第几轮」并不是它天然知道的事。R12 要的三件事补齐如下：

| 问题 | 答案 |
|---|---|
| 状态存哪 | `runtime.json` 里一个 `carriedSessions: { <sess>: <ts> }` 映射（2026-11-04 从 `state.json` 移出）。它是**运行账本**，不是派生态：可丢、丢了允许重新 carry，30 天清理 |
| 怎么判定 | 组装 L0 时拿宿主给的 `sess`（§3.1 的同一个字段）查这个映射：**不在映射里 = 第 1 轮**，于是注入 carry 并把 `sess → now` 写进去；已在映射里就不注入。判据是「这个会话 id 有没有被 carry 过」，不是时间窗 |
| 为什么不用时间 | 「距会话创建 <N 秒算第 1 轮」会被时钟漂移（§13-6）和长耗时的首轮工具调用打穿，而且无法区分「同一会话的第 2 轮」和「另一个刚建的会话」 |
| 并发两个会话 | 各自有各自的 `sess`，映射里是两个独立键，各 carry 一次，互不影响、不会重复，也不会互相抑制。两个会话同时写该映射时由同一把锁串行，后写者看到的是合并后的结果（写前重读，§4.5 的 tmp→rename 保证读者不会看到半截） |
| 清理 | `runtime.json` 里的 `carriedSessions` 按 30 天清理。它只是防重复注入的去重表，过期条目没有价值 |

注意 carry 的幂等性由 `runtime.json` 负责：若该文件被删（或换机），`carriedSessions` 会丢失，正在进行的会话可能**再 carry 一次**。这是可接受的退化——多注入一次 800 字符，不产生事件（carry 不写盘，见下一段），不污染任何数据。

carry 搬原文不搬摘要。样本 B 的注释说得对：「总结出来的东西是别人替她讲的。搬运是诚实的，总结是不诚实的」。但本系统搬的是**事件原文**而不是对话原话——我们记的是主人的事，不是对话过程，L1 里的 `text` 本身就已经是被筛过的陈述句。

carry **不产生新事件**。否则每次换会话都会把最近 6 条复读成新的 6 条，几轮之后事件流全是自己的回声。

### 6.6 L2 召回的调用时机

写进 agent instructions 的触发条件（不是硬编码逻辑，是给模型的规则）：

1. 主人提到一个**具体名词**（路径、文件名、工具名、人名、项目名）而当前上下文里没有它的解释；
2. 主人说「上次 / 之前 / 你不是说过」这类回指；
3. **（强制）** agent 准备做一个**有副作用**的操作（写文件、改配置、跑命令、commit）之前，且 L0 尾注显示有红线溢出时，必须先调 `mem_recall(kinds=['rule'])`（§6.3）；无溢出时此步可省，因为红线已全在 L0；
4. 主人问「为什么当初……」。

反面规则同样重要：**闲聊、问候、纯代码生成不要召回**。每次召回都要花一轮工具调用和 ≤800 字符，无差别召回等于把 L0 的预算控制白做。

## 7. 检索算法

### 7.1 中文分词：bigram + 停用字，不要 919 KB 词表

方案：
1. 归一化：全角转半角、去标点、ASCII 转小写、合并空白。
2. 切分：
   - 连续的 ASCII / 数字段作为**整词**（`pnpm`、`0.2.1`、`events.jsonl` 不切）；
   - 连续中文段按 **2-gram 滑窗**切（「包管理器」→「包管」「管理」「理器」）；
   - 单字中文只在**整个查询只有 1 个汉字**时才作为词元（避免「的」「了」这种噪声）。
3. 停用：一张约 150 字的停用字表（的 了 是 在 有 和 就 也 都 吗 呢 把 被 给 让 ……），命中即丢弃该 gram。表是硬编码常量，约 1 KB。

**为什么不用 jieba 词表**：919 KB 的词表要打包进插件、启动时加载进内存、还要维护。硬约束 G10 是零或极少第三方依赖，单机单人场景下不值得。代价是精确率下降（bigram 会把「管理」从「包管理器」和「项目管理」里都切出来），补偿手段见 §7.2 的 `maxRunLen` 项：**连续命中越长，得分超线性上升**，所以「包管理器」会显著压过只命中「管理」的条目。

**另一种做法为什么不行**：按单字切（1-gram）召回率最高但精确率灾难性——中文常用字就那几千个，任何查询都会命中半个库。样本 B 的「≥3 字才切二字切片」是一个更保守的变体，它在 2 字查询上退化为整串精确匹配，会漏掉「作息」匹配「主人的作息时间」这类情况。本方案统一用 2-gram 不设门槛。

### 7.2 评分公式

```
score(e, q) = base(e, q) × w_kind(e) × w_imp(e) × decay(e) × penalty(e) + ref_bonus(e)

base(e,q)   = Σ_{g ∈ hits}  len(g)^1.5 / (1 + ln(1 + df(g)))      # idf 抑制高频 gram
            + 2.0 × maxRunLen(e, q)                                # 最长连续命中字数
            + 3.0 × [q 与 e.key 的某一段精确相等]
            + 1.5 × [q 中出现 e 的 tag]
            + aliasBonus(e, q)     # 2026-11-04：min(8, 2L)，L = q 整句包含的最长已批准俗称字数
            # 别名表扩展出的 gram 按 0.8 折计入上面的 Σ；俗称（aliases）不走 Σ，直接加这一项。
            # 两者都不进 eventSearchText，所以不影响 df。

w_kind      = rule 1.0 | decision 1.2 | todo 1.1 | fact 1.0 | note 0.9   # rule 不加成，见 §7.3
              # 纠正类必须显式给权重，否则公式对它们无定义（此前漏了这三项）：
              # revise 0.8 —— 纠正后的新说法可以被召回，但排在同类 note 之后
              # retract 0.0 / close 0.0 —— 撤销与关单只是动作，不携带可召回的内容
# 本节公式只服务 L2 召回。L0 四段各有自己的排序（§6.2），一概不走这里。
w_imp       = 0.8 + 0.2 × weight                       # weight∈1..5 → 1.0..1.8
decay       = max(0.15, 0.5 ^ (ageDays / halfLife))    # 不删，只降权（抄样本 C）
              halfLife: rule=∞ | decision=365d | fact=180d | note=90d | todo=30d
              固化条目（§8.2）halfLife ×3
penalty     = active 1.0 | closed 0.10 | superseded 0.02 | revised 0.02 | retracted 0.0
ref_bonus   = 0.5 × min(3, 肯定性被引次数)             # 仅来自 active 的 decision / note
```

### 7.3 rule 在排序里不加成，但保留一个条件席位（R3：部分接受）

**接受 R3 的核心判断**：`w_kind(rule)=1.4` 是错的，已改成 1.0。R3 的论据站得住——全局加成是一个**无差别**的手段，它让红线在每一次召回里都往前挤，包括那些跟红线毫无关系的查询。「主人问某个坑，第一条永远是红线」是加成的必然结果，不是副作用。要表达「红线重要」，不该用排序权重这个工具：排序权重表达的是「相关性」，而红线的重要性和相关性是两回事。

**但不接受把 rule 降成 1.0 之后就不管了。** R3 邀请我给一个「不加成会导致红线漏掉且 L0 兜不住」的具体场景，这个场景存在，而且是 R2 刚刚造出来的：

> 主人有 9 条红线。按 §6.3，L0 只常驻前 6 条，第 7–9 条**不在 L0**。
> 其中第 9 条是：「改 `whale-chan-fixed.yml` 之前必须先备份，上次没备份丢过 270 行」。
> 主人说「帮我把 whale-chan-fixed.yml 的 maxChars 调一下」。
> agent 调 `mem_recall("whale-chan-fixed.yml maxChars")`——这是一次**普通查询**，不是 `kinds=['rule']`。
> 库里关于这个文件有 5 条 `note`（第 109 行在哪、怎么 Select-String、插件行格式……），每条都在文件名上有超长连续命中。
> `limit=4`，`w_kind(rule)=1.0`，第 9 条红线排第 5 → **被挤掉**。
> L0 兜不住（它不在 L0）。agent 直接开改，没备份。

有人会说：§6.6 触发条件 3 不是强制要求「有副作用操作前先调红线通道」吗？是的，但**那是一条写给模型的提示词规则，不是代码保证**。模型会跳过提示词规则，这是已知事实；本文档 §11.2 还专门为「persona 被覆盖导致记忆静默失效」设计了自检，就是因为不信任提示词层面的保证。在模型**已经调用了**召回的这条路径上，我们有能力在代码层给一个保证，就不该把它让给提示词。

所以加一条**条件席位**规则：

> 在 `kinds` 未显式指定的普通召回中，为 `rule` 保留**最多 1 个**名额，当且仅当同时满足：
> (a) 该 rule 的 `base` 分 ≥ 阈值 1.0（即它**真的在字面上命中了这次查询**）；
> (b) 该 rule **当前不在 L0 常驻段**里（在 L0 的已经在上下文中，再占一个名额是纯浪费）；
> (c) 它没有凭自身分数进前 `limit`（进了就不需要席位）。
> 满足则替换掉原结果的最后一名，并标注 `[红线]` 前缀。

**两条实现细则（2026-11-02 P4 补，都是踩过的坑）**：

1. **「在不在 L0」要用结构性判据**。拿 L0 渲染出来的**字符串**去 `includes` 比对 id 是脆的：正文里可能恰巧出现同样的字符序列，id 也可能被截断修饰（`…(m_xxx)`）。要求 `renderPinned` 同源导出一个 `pinnedIds(state)`，席位判断只认这个集合。
2. **席位优先于字数预算**。若席位规则的文本会把总字数顶过 800，正确做法是**挤掉普通结果里最不相关的一条**再放席位，而不是让 `packItems` 的「放不下就跳过」把席位悄悄丢掉——那等于红线有席位却永远坐不上。§12 的 A10b 守这条。

这条规则为什么**不会**重新制造 R3 抱怨的问题：席位的前提 (a) 是字面命中。R3 的场景「主人问某个坑」里没有任何红线会命中「坑」的查询词，`base` 为 0，席位不触发，结果里一条红线都不会出现。加成是无条件的，席位是有条件的——**这正是两者的区别**。

代价讲清楚：最坏情况下 4 个名额被占掉 1 个，且只在「有红线字面命中、且该红线不在 L0」时发生。用 1/4 的名额换一个代码层的红线保证，这个交换值得。验收用例 A24（席位生效）与 A25（无关查询不触发席位）成对守住两侧。

### 7.4 被取代的条目必须降权到底

这是本设计对样本 B 已知缺陷的正面回答，三条规则缺一不可：

1. **penalty 是乘子不是减项**。`superseded` / `revised` 乘 0.02，意味着一条被取代的条目即使在文本上完美命中，也要分数超过第一名 50 倍才可能冒头——实际上不可能。用减项（如 `score - 10`）则高分条目仍能幸存。
2. **否定性引用不加分**。`revise` / `retract` 对被引用条目的引用**不计入** `ref_bonus`。样本 B 正是在这里出的问题：它把一切 `refs` 一视同仁，结果「被推翻过的原句」因为被引用过而加了 3 分，排名反超正确的新句。
3. **`retracted` 的 penalty 是 0，彻底不召回**。被撤销 ≠ 被取代：撤销说的是「这事根本不该记」，它不该出现在任何召回结果里，只在 `mem_audit` 里可见。

`includeSuperseded: true` 是唯一的例外通道（penalty 提升到 0.5），供「主人问历史」时使用，默认 `false`。即便开启，结果里每条也必须带 `[已被 m_xxxx 取代]` 前缀——**绝不能让一条过期的事实看起来像当前的事实**。

### 7.5 封顶策略

`mem_recall(query?, limit<=6, maxChars<=800, kinds?, since?, includeSuperseded=false)`：

- `limit` 默认 4，硬上限 6；
- 单条 ≤200 字符（超长截断并加 `…`，id 保留）；
- 总字符 ≤800，逐条累加，放不下就停；
- 低于绝对阈值 `score < 1.0` 的一律不返回，**宁可返回 0 条也不返回噪声**；
- 返回体结构：`{ receipt_id, items: [{id, ts, kind, text, key?, status?}] }`。

唯一的例外是 §6.3 的红线通道（`kinds=['rule']`）：`limit≤12`、`maxChars≤1200`、无分数阈值、`query` 可省。除此之外所有参数组合都受上表约束。

**返回体里没有 `total`、没有 `hasMore`、没有「还有 N 条」**（G6）。理由：这类字段会诱导模型连续追加召回，把 §6.6 的节制规则冲掉。要看更多走 `mem_audit(what="recall", receipt_id=...)`，那是给人和审计用的路径，不在主对话流里。

## 8. 遗忘与折叠

### 8.1 什么该淡出

没有任何条目会因为「排队排到了」而消失——**不做 FIFO**。

样本 A 的 80 条 FIFO 把「主人的红线」和「上周随口一句」放进同一个队列，按入队顺序出局。本机记忆本里已经能看到后果：滚动区 15 条里有 6 条是调试过程的流水账（「等用户重启 DSH 加载」），它们和「plan-mode 的三条硬约束」占同样的名额。

淡出靠 `decay`：时间越久分数越低，下限 0.15。一条三年没被用过的 `note` 分数降到 15%，实际上永远排不进 top4，但它仍然在盘上，`mem_audit(what="id")` 查得到，也可能因为某天主人正好问到而命中（它的 `base` 分会很高，足以抵消 decay）。

### 8.2 什么该固化

条目满足任一条件即标记 `solid: true`，`halfLife ×3`，并获得进入 L0 事实段的资格：

- 同一 `key` 被 ≥3 次独立写入确认（`confirmCount[key] >= 3`，取代也算确认，说明这个键确实在被持续关注）；
- 被 ≥1 条 active 的 `rule` 或 `decision` 肯定性引用；
- `weight >= 4` 且 `kind in {rule, fact}`；
- 最近 30 天内被 `mem_recall` 实际选中 ≥3 次（从 `recall-log.jsonl` 统计——**实际用到才算重要**，比任何先验权重都准）。

`rule` 天生不衰减，不需要固化。

### 8.3 容量与折叠（不是 FIFO）

触发条件：`events.jsonl` 行数 > 20000 **或** 体积 > 8 MB。

折叠的筛选条件是**状态 + 年龄**，不是顺序：

| 条目 | 处理 |
|---|---|
| `status=active`（任何 kind、任何年龄） | **永不折叠** |
| `superseded` / `revised` / `closed` 且 `ts` 早于 180 天 | 搬去 `archive/YYYY-Qn.jsonl` |
| `retracted` 且早于 180 天 | 搬去 archive |
| `revise` / `retract` / `close` 事件本身，其 refs 全部已折叠 | 一并搬走 |

折叠流程（这是**唯一**允许重写 `events.jsonl` 的操作）：

```
1. 持锁；2. 复制 events.jsonl → archive/snapshot-<ts>.jsonl（全量备份，失败则中止）
3. 选出待折叠行，追加写入 archive/YYYY-Qn.jsonl，fsync
4. 向 events.jsonl 追加一条 fold 事件：
   {"kind":"fold","ts":...,"foldedCount":N,"into":"archive/2026-Q4.jsonl",
    "sha256":"<被折叠行拼接的摘要>","idRange":["m_aaa","m_zzz"]}
5. 以 tmp→rename 重写 events.jsonl 为「去掉已折叠行」的新文件
6. 全量 derive，校验条目总数 == 新 events 条数 + archive 条数；7. 释放锁
```

**诚实说明**：第 5 步破坏了「只追加」。这是一个**明知的取舍**——不折叠的话，几年后每次启动要解析几十万行。补偿措施是：有全量快照（第 2 步）、有 fold 事件记录区间和校验和（第 4 步）、有折叠后的条目数校验（第 6 步），所以这次重写是**可审计、可回溯、可验证**的，而不是悄悄发生的。`archive/*.jsonl` 仍然是真相的一部分，derive 时会一并读入。

**另一种做法为什么不行**：永不重写，改成 `events-001.jsonl` / `events-002.jsonl` 分段追加。这确实能保住纯粹的只追加，但读取路径要处理分段列举和顺序，坏一段就断链，而且「哪些条目已经没用了」的信息完全丢失——文件数会无限增长。见 §13。

### 8.4 为什么不引入后台 LLM 做整理

一个「定期把零散条目合并成精炼条目」的后台 agent 听起来很美，但它违反 G4：合并就是改写，改写就是静默篡改。而且它引入了一个没有人监督的写入者——出错时主人看到的是「记忆变了但没人知道为什么」。宁可留着零散条目靠评分压住，也不要一个会自己改历史的东西。

## 9. 审计与可观测

### 9.1 召回回执

每次 `mem_recall` 向 `recall-log.jsonl` 追加一条（2026-11-05 起：攒到 260 条再裁回 200，且落盘每条只留得分前 5 的候选——原来的写法是每次追加都把整个文件重写到 200 条，见 §16.4；仍不依赖折叠，折叠是按季度触发的，靠它会让回执无限长）。它是审计流不是真相源，但**可读**：`mem_audit(what="recall")` 读最近一次或指定 `receipt_id`，`§8.2` 的固化判据也从这里统计「30 天内被选中 ≥3 次」。上一版说它「只写不读」是自相矛盾的，已改。

下面是**内存版**回执（完整打分分量，`onReceipt` 回调拿到的就是它）；落盘版把每个候选压成 `id` / `score` / `why` / `base` 四个字段、只留前 5 名，另加一个 `candidateCount` 记原始候选总数（见 §16.4）：

```json
{"receipt_id":"r_lqd9a1","ts":"...","query":"包管理器","grams":["包管","管理","理器"],"picked":["m_lqd55e"],"chars":58,
 "candidates":[
  {"id":"m_lqd55e","score":12.4,"base":9.1,"kind":1.0,"imp":1.4,"decay":1.0,"penalty":1.0,"refs":0,"picked":true},
  {"id":"m_lq8f41","score":0.21,"base":9.0,"kind":1.0,"imp":1.4,"decay":1.0,"penalty":0.02,"refs":0,"picked":false,"why":"状态降权:superseded(被 m_lqd55e 取代)"}]}
```

`mem_audit(what="recall")` 返回最近一次（或指定 `receipt_id`）的候选表。未入选原因是枚举，不是自由文本：

| 原因码 | 含义 |
|---|---|
| `低于阈值` | `score < 1.0` |
| `状态降权` | superseded / revised / retracted / closed，附上取代者 id |
| `超条数上限` | 排在 limit 之后 |
| `超字数上限` | 排名够但总字数放不下 |
| `kinds过滤` / `since过滤` | 被调用参数排除 |
| `未命中` | base 为 0，一个 gram 都没中 |
| `让位红线席位` | 原本是最后一名，被 §7.3 的条件席位替换掉 |

这直接回答 G9 的「这条为什么没被选中」。样本 C 的设置页「最近一次召回」表是对的思路，本设计把它做成工具返回值而不是 UI——因为 agent 自己也需要在被主人质问时查这个。

### 9.2 记忆体检

`mem_audit(what="health")` 返回六张清单：

| 清单 | 判据 | 为什么要看 |
|---|---|---|
| **对不上的话** | 同一 `key` 存在 ≥2 条 `active` 的 `fact` | 取代链断了（通常是 derive 崩在半路），必须人工介入 |
| **快忘的** | `active` 且 `decay < 0.25` 且 90 天未被召回选中，top 10 | 主人可以决定提 `weight` 或让它继续沉 |
| **快固化的** | `confirmCount[key] == 2`（差一次到 3） | 提示这个键正在变成长期事实 |
| **被取代的** | 最近 30 天内 `superseded` / `revised` 的条目及其取代者 | 回答 G9 的「哪些被取代了」 |
| **疑似该用 fact** | `note` 文本命中任一**已有 key 的「方面」段**（比 §5.3 的 3a 宽：不要求对象段同时出现） | 3a 漏网的改写句式（「包管理器换成 npm 了」）、本该带键却没带键的记录，交给人回看。只读派生视图，**不写入、不影响召回分** |
| **健康指标** | `corruptLines`（本次扫描的坏行数，见 §16.1）、`corruptLinesEver`（历史峰值）、`lock_stolen` 次数、`sourceHash` 是否匹配、events 行数/体积、距离折叠阈值还剩多少、`rules_overflow`（红线真有损失，见 §6.2 §16.2）、`rules_near_limit`（一行没丢但名义宽度超配额，见 §16.2）、`rules_truncated_hard`（红线正文被压到 16 / 8 字的硬截断，见 §6.2）、`injection_missing`（L0 没进最终提示，见 §11.2） | 运维。**这几个字段是 health 的正式成员**，A5/A18 的断言依赖它们 |

### 9.3 重建自检

`state.json` 里存 `sourceHash = {lines, lastId, sha16}`。插件启动时读 `events.jsonl` 的行数与末行 id 比对：

- 匹配 → 直接用 `state.json`（快路径，不用解析全文）；
- 不匹配 → 全量 derive，并在 `health.json` 记一次 `rebuilt`，附原因（行数差 N 行）。

这条机制同时覆盖了三种故障：写派生品时崩溃、外部手工编辑 `events.jsonl`、多进程抢锁失败导致的漏算。

### 9.4 备份

- 折叠前自动 `archive/snapshot-<ts>.jsonl`（§8.3 第 2 步）；
- 没有自动定时备份。理由：真相源只追加，本身就是自己的历史，不需要快照才能回到过去。

**git 策略：默认不进版本库（R7：接受）。** 初版在 §13 把这条列成「没有好答案」的开放问题，评审 R7 的判决是对的，论据我接受并补强：隐私泄露是**不可逆**的（推到远端的那一刻就无法收回，改历史也救不了已经 clone 的副本），而版本历史是**可替代**的收益——L1 只追加，它本身就是一部完整的历史，这正是 §9.4 开头那句「不需要快照才能回到过去」的意思。拿不可逆的损失去换一个已经有替代品的收益，是坏交易。两头都要等于两头都不牢。

落地方式：插件初始化 `.dsh-mem/` 时，在目录内写一个**自忽略**文件：

```
# .dsh-mem/.gitignore
*
```

这样整个目录对 git 不可见，且**不需要修改工作区根目录的 `.gitignore`**——后者是主人的文件，插件不该去动它；而且根 `.gitignore` 可能本身就被 git 管理，改它反而会产生一个需要主人解释的 diff。自忽略文件随记忆目录一起创建、一起删除，生命周期干净。验收用例 A26。

想要版本化的主人怎么办：明确**不提供** `git add -f` 这条路（那等于把隐私问题原样搬回来），而是指向 §9.4 第一条——把 `events.jsonl` 复制到工作区外的任意位置自行管理。这是一个需要主人主动做、且做的时候知道自己在做什么的动作。

### 9.5 L0 配额指标怎么读（运维速查）

上一节和 §6.2 各讲了一半，这里汇成一处：四个指标同源——都产生于 L0 渲染，由 `persistPinnedHealth` 每轮写进 `health.json`，再被 `mem_audit(what="health")` 原样透出。它们**不是历史累积状态**，而是「这一轮组装出来的样子」。

| 指标 | 什么时候为 `true` | 意味着什么 | 该做什么 |
|---|---|---|---|
| `rules_overflow` | 红线被挤出前 6 条，或任一条正文 > 32 字被压，或 `rules_truncated_hard`（2026-11-05 改成只算真实损失，见 §16.2） | 至少一条红线的**正文不完整** | 看尾注分辨：写「另有 N 条红线未常驻」是有溢出，先跑 `mem_recall(kinds=['rule'])`；写「红线内容已截断」只是单条太长 |
| `rules_near_limit` | 一行没丢、正文没压，但红线段名义宽度 > 300 字配额（§16.2） | 内容**是完整的**，只是接近上限，再加一条就可能真溢出 | 不用动；尾注写「红线已接近配额」时，考虑合并或精简红线 |
| `rules_truncated_hard` | 总预算顶穿，红线正文被压到 16 或 8 字（§6.2 最后两级降级） | 红线只剩**存在性**，正文基本没了 | 立刻处理：删/合并红线，把细节挪进 `note`。这一级不该长期为 `true` |
| `injection_missing` | 最终提示里找不到 L0 首行（§11.2） | 记忆**这一轮根本没进去** | 查 persona 有没有 `{{owner_memory}}`；只在**最终文本**或**名单里的 preset** 上判定。组装阶段（`system-prompt/assemble`）拿到的还是未插值的 `{{owner_memory}}` 字面量，那时不判「缺失」 |

读法三条：

1. **两个 `rules_*` 常态为 `false`，而且必须是能回落的 `false`。** 写一条长红线再删掉，值应该从 `true` 回到 `false`——只升不降的指标等于没有（用例 `l0-health-persist` 守的正是这条）。
2. **尾注和指标口径必须一致。** 尾注说「红线内容已截断」而 `rules_overflow` 却是 `false`，说明落盘链路断了（§6.2 记的那个漏洞），先看 `health.json` 的 mtime 是不是本轮时刻：不是，就是自检没在跑；是，才是判定逻辑错。
3. **单条红线 ≤ 32 字是让这两个指标长期为 `false` 的唯一写法。** 正文写「一句话命令」，解释、事故经过、复现步骤全放 `note`。这条本身也是一条红线（`mem_note` kind=rule，weight 4），2026-11-03 由「两条 90 字红线永远被截半句」这个事故换来的。

自查两条命令：

```
mem_audit(what="health")                  # 看 rules_overflow / rules_truncated_hard / injection_missing
Get-Item .dsh-mem/health.json             # mtime 应等于本轮的组装时刻
```

## 10. 迁移方案：从 loli 四区 md 导入

> **状态：历史记录（2026-11-03）。** 对应的 `mem_migrate` 工具与其实现 `src/migrate.js` 已删除，A12 / A13 验收用例随之撤除；本机迁移是手工筛的（41 条事件里 `src=migrate:loli` 零条）。本节保留设计思路，供将来真要再做批量导入时参考，不要照着它去找工具。

### 10.1 解析规则

源文件：`~/.dsh/whale-chan-memory.md`（+ `~/.dsh/archive/whale-chan-memory/*.md`）。
分区标题常量来自 `memory.js`：`# 固定记忆` / `# 滚动摘要` / `# 最近详细区` / `# 归档索引`（标题后可能跟括号说明，用 `startsWith` 判定而不是全等）。

| 源区 | 解析 | 产出 |
|---|---|---|
| `# 固定记忆` 下的 `## 小节` | 每个 `- ` bullet 一条 | `kind` 由小节标题映射（见下表），`weight=4`，`pin=true` |
| `# 滚动摘要` | 正则 `^-\s+(R\d+)\s+\[([^\]]+)\]\s*(?:摘要[：:])?\s*(.+)$` | `kind=note`，`weight=2`，`legacy_id=R0001` |
| `# 最近详细区` | 同上正则 | 按 `legacy_id` **去重后跳过** |
| `# 归档索引` | 行形如 `- archive/<stem>/<date>.md（N 条）`，按路径读取归档文件，用滚动区规则解析 | 同滚动区 |

小节标题映射：

| 小节 | kind | tags |
|---|---|---|
| `## 关键事实（已验证）` | `fact`（能起键）/ `note`（起不出） | `验证` |
| `## 环境与约束` | `rule` | `红线` |
| `## 错误与修复` | `note` | `坑` |
| 其它小节 | `note` | 小节标题原文作为 tag |

时间：方括号里形如 `2026-11-02 04:07`，无年份则补源文件 `mtime` 的年份，时区按本机。固定区 bullet 没有时间 → 用源文件的 `birthtime`，并在 `text` 前加 `（时间不详，迁移自 loli 固定记忆）`。**不伪造精确时间**，G2 要求能回答「什么时候的事」，「不详」是一个诚实的答案。

### 10.2 为什么跳过「最近详细区」

本机实测该区与滚动区逐条重复（R0001–R0015 完全一致），它本来的设计意图是「保留更详细摘要或原文」，但实现上写入的是同一份文本。更糟的是，该区已被 read-modify-write 的并发覆盖破坏，出现 `...已写盘,- R0006 [2026-11-02 05:09] ...` 这样的逗号粘连行。

处理：先按 `,(?=-\s+R\d{4}\s+\[)` 二次切分把粘连行拆开，再按 `legacy_id` 与滚动区去重。若拆出来的某条 `legacy_id` 在滚动区**不存在**（说明是被滚出去的旧条目），则保留并导入。

### 10.3 残留与不丢保证

任何无法匹配上述规则的非空行，**不丢弃**，归成一条 `kind=note, tags=["迁移残留"], text="<原文 ≤200 字符>"`。超过 200 字符的整段落拆成多条并在 text 前加 `(1/3)` 之类的序号。

验收等式 —— `导入条目数 == 固定区 bullet 数 + 滚动区条目数 + 归档条目数 + 残留段数 −（详细区与滚动区的重复数）`。这个等式写进验收用例 **A12**（迁移不丢；此前误写成 A7，A7 是「revise 不给原条加分」，与迁移无关），幂等性归 **A13**。迁移工具的 `dry_run` 输出里直接打印左右两边。

### 10.4 幂等性

每条迁移事件的 id 是**确定性**的：`m_mig_` + `sha1(legacy_id + ts + text).slice(0, 10)`。

- `state.json` 里维护 `migratedIds: Set<string>`；
- 追加前查集合，已存在则跳过并计入 `skipped`；
- 所以同一份 md 重跑 N 次，结果与跑 1 次完全相同。

源文件处理：**不删除**，迁移成功后改名 `whale-chan-memory.migrated-<ts>.md` 留底。改名而不是删除，是因为迁移的解析规则很可能第一次写不对，需要留着重试。

`mem_migrate(path, dry_run=true)` 默认只做解析与统计，打印分区条目数、映射结果采样 10 条、残留段清单、验收等式两边的值。确认无误后 `dry_run=false` 才真写。

### 11.1 插件行

### 11.2 变量通道 vs 独立 section

**必须用变量通道。** C3 的证据链是完整的：`persona` 是 `complete: true`，宿主会丢弃其它 section，`memory.js` 顶部注释写明了这一点，本机实测「34 条真实系统提示里记忆段出现 0 次」。独立 section 在当前宿主下就是不生效。

变量通道的代价要写清楚：

| 代价 | 缓解 |
|---|---|
| `{{owner_memory}}` 要手写进 persona prefix，与人设文本耦合 | 本地 patch 的 persona 本来就是手写维护的（provenance 文档里说明不跟上游同步），耦合可接受 |
| persona 被上游覆盖 → 变量引用消失 → 记忆**静默失效** | 自检改为 `judgeInjection`（2026-11-04 定稿，Opus 定规则 / Sol 验可行）：只在 `system-prompt/assemble` 中间件与 provider 包装器两处取证，**`missing` 只认三种确定信号**——`variables` 里没注册（`not_registered`）、引用段 `interpolate === false`（`interpolate_off`）、provider 抛异常且有引用证据（`provider_error`）；其余一律 `deferred`，宁可不判也不误报。不再用 `session.header.agentPreset` 当期望值（那是记录，不是事实），也不再依赖 `sp.afterRender`——**宿主根本没有这个 API**，旧的 `checkText` 从未执行过 |

静默失效是样本 A 最隐蔽的问题（记忆写了一堆，但从没进过上下文，没人发现）。自检这一条是必须的，不是可选的。

**为什么不挂 `agent-instructions`**：它的内容是静态文件 + `maxBytes: 65536`，不走每轮重读，改完记忆要重启才生效。而变量通道每次组装都重新读盘（现有 `whale-memory` 就是这个行为），改完下一个模型步就生效。

### 11.3 工具注册

五个工具（§5.1）全部注册在同一插件行下，宿主进程内执行 fs。不走 agent 的 `shell`/`edit`，所以不触发 C1 的沙箱拒绝，也不触发 C5 的 `file changed since it was read`（那是 `edit` 工具的观察策略，与宿主 fs 无关）。

工具描述文案里要明确四件事，因为模型只看描述：
1. 三个写工具都只会**新增**，不存在修改已有条目的方法；
2. 选哪个写工具，用 §5.3 的是非问句判定，描述里各带 3 正例 3 反例；
3. 改变一个事实就用同 `key` 的 `mem_fact`，纠正一个错误用 `mem_fix(op='revise')`；
4. `mem_recall` 不要无差别调用，触发条件见 §6.6。

### 11.4 会话级开关

三级，从粗到细：

| 级别 | 方式 | 效果 |
|---|---|---|
| 工作区 | `.dsh-mem/disabled` 文件存在 | 只读模式：仍注入 L0、仍可 recall，但三个写工具（`mem_fact`/`mem_note`/`mem_fix`）一律返回 `E_DISABLED` |
| 工作区 | 整个 `.dsh-mem/` 不存在且 `autoCreate: false` | 完全停用，不注入不注册 |
| 会话 | `mem_audit(what="status")` 只读查看当前开关 | 开关不走工具，避免模型自己把记忆关掉 |

**为什么不给模型一个「关闭记忆」的工具**：陪伴型 agent 的记忆被它自己关掉，主人无从察觉。开关是主人的权力，走文件。

### 11.5 共存与边界：三套记忆同时活着（R5：接受，列为上线阻断项）

初版完全没写这一节，这是一个真实的疏漏——设计一套新记忆时假装现场是空地，而现场并不是。本机实测的现状：

| 系统 | 存储 | 挂载方式 | 工具 | 实际写入量 |
|---|---|---|---|---|
| loli `whale-memory` | `~/.dsh/whale-chan-memory.md` | 本地 `cordis.patch.yml` 第 109–118 行，变量 `{{whale_memory}}`，`maxChars: 16000` | `whale_memory_add` | **在用**：固定区 3 小节 + 滚动区 R0001–R0015 |
| `dsh-fish` | `~/.dsh-fish/events.jsonl` | `package.json` 的 `dsh.profile.bundles` 列表，包内 `cordis.patch.yml` 只有一行 `- id: dsh-fish`；本地 patch 里**零匹配** | `growth_commit` / `her_recall` / `her_say` / `her_diary` / `her_dream` / `her_leave` | **几乎为空**：`events.jsonl` 只有 2 行，且都是系统自己写的（`type:seed` 的种子句 + `type:meta` 的定时器记录），没有任何一条来自 agent 的 `growth_commit` |
| 本设计 `owner-memory` | `<workspace>/.dsh-mem/` | 待接入 | `mem_fact` / `mem_note` / `mem_fix` / `mem_recall` / `mem_audit` / `mem_migrate` | 未上线 |

这张表改变了结论。R5 问「`her_*` 那套要不要停」——**要停，而且成本接近零**：fish 的事件流里没有任何真实内容，停用它不会丢任何主人的事。它那 6 个工具目前的净效果是占掉 6 个工具名额、给模型 6 个会分散注意力的选项，而 `growth_commit` 的语义（utterance / dream / diary / refusal）与「记主人的事」正交——模型若误用它写主人的偏好，那条记忆会落进一个本设计永远不会读的文件里，**静默丢失**。这是比「重复注入」更危险的失败模式。

### 11.6 重复注入的实际风险

三套都开会不会重复注入？分三种情况，结论不同：

| 组合 | 会不会撞 | 原因 |
|---|---|---|
| loli + owner-memory | **会**，且很严重 | 两者都走变量通道注入 persona prefix。loli 的 `maxChars: 16000` 会把 L0 的 1200 预算彻底淹没，G5 直接失效 |
| fish + owner-memory | 不会撞预算 | fish 不在本地 patch 里注册任何 prompt 行，它的注入走自己包内的 persona 行；但**会撞工具语义**（见上一节） |
| loli + fish | 已经是当前状态 | 两者互不相通，各写各的 |

所以阻断项只有一条是硬的：**loli 与 owner-memory 不得同时启用变量注入**。

### 11.7 切换期：双写、单读、可回滚

迁移不是一次性开关，分三阶段，每阶段有明确的回滚动作：

| 阶段 | loli | fish | owner-memory | 读谁 | 回滚动作 |
|---|---|---|---|---|---|
| **P0 并行观察**（1–3 天） | 保持启用，变量仍注入 | 保持现状 | 装上，注册工具，`mem_migrate(dry_run=true)` 跑通，**但变量不接进 persona** | loli | 删 `.dsh-mem/` 即可，零影响 |
| **P1 切读**（观察 ≥1 周） | 插件行加 `disabled: true`，`{{whale_memory}}` 从 persona 移除；**文件原样保留** | `bundles` 里移除 `dsh-fish`，6 个工具下线 | `mem_migrate(dry_run=false)` 执行；`{{owner_memory}}` 接进 persona | owner-memory | 把 `disabled` 去掉、变量换回 `{{whale_memory}}`，loli 文件一个字没动，立刻恢复 |
| **P2 收尾** | 源文件改名 `.migrated-<ts>.md`（§10.4） | 可从 `package.json` 依赖里删除 | 唯一记忆系统 | owner-memory | 改回文件名即可回到 P1 |

**为什么不做「双写」**（同时往 loli 和 owner-memory 写）：双写要求两边语义能对上，而 loli 只有「滚动摘要」一种结构，承载不了 `key` / `refs` / `status`。强行双写的结果是 loli 侧退化成一堆没有取代关系的摘要——等于一边做着正确的事，一边继续生产将来还要再迁一次的垃圾。**正确的做法是单写 + 保留旧文件不动**：旧文件是一份静止的、随时可回滚的快照，这比一份持续劣化的副本有用得多。

**P1 为什么要观察一周**：L0 注入上限（A4）、红线席位（A24）、dedup 阈值（A22）这三件事都只有在真实使用里才能暴露参数拍错。一周是「至少跨一个工作日周期」的下限。

**上线阻断清单**（全部通过才能进 P1）：§12 的 A1–A28 全绿（A12 / A13 随 `mem_migrate` 删除而失效，见 §5.1）；~~`mem_migrate(dry_run=true)` 的条目数等式（§10.3）左右相等~~（该工具 2026-11-03 已删除，此项作废）；A18 变量到达自检为真（否则就是又一次「写了一堆从没进过上下文」）；loli 插件行确已 `disabled: true` 且 persona 里无 `{{whale_memory}}`——**最后这两件事必须同时做**，只做一件会导致变量未定义，具体渲染成空串还是字面量取决于宿主，两种都不可接受。

## 12. 验收标准

## 15. 2026-11-04 落地变更（与上文冲突时以本节为准）

### 15.1 纠正语义（P0）

- **`revise` 继承 key**：`refs` 恰好 1 条、是当前值、且事件自带同 key 时，修订句成为该键的新当前值（状态仍 `revised`）；`weight` 取新旧较大值，`tags`/`pin` 照抄。理由是「回退到上一条」在「上一条也错」的场景下会留一个错值。→ §3.4 §5.5
- **`mem_note` 新增 `replaces`**：与 `refs` 分开存放；被取代方变 `superseded`、`supersededBy` 指向新条，**不给 `ref_bonus`**；仅同 kind、排除 fact、目标须 active；撤销新条时按 `prevStatus`（完整状态对象）复活。→ §3.4 §7.2

### 15.7 L0 事实段的「结论可见」（headline）

原渲染 `[项目] YY-MM-DD <正文前 32 字>…(id)` 按字符位置盲切，而我们的书写习惯常常「路径在前、结论在后」，于是结论被切掉。两次现场：`cookie位置` 只剩路径看不到「能不能发」；金丝雀探针的颜色正好被切在 32 字之外。

- **落盘**：`mem_fact` 新增可选 `headline`（1–18 字，不含换行）。带 headline 的走新格式，不带的**完全保留旧格式**（不做「首句 18 字」兜底——实测那样会切出「2026-11-04 18:00 起」这种更像结论的残句）。
- **书写约束**：不要在 headline 里写日期（日期由 L0 渲染负责，跨年会自动切 `MM-DD` / `YY-MM-DD`），也不要重复对象名（对象已由标签承载）。
- **新格式**：`[主人|项目] <日期> <对象简称>.<方面段>：<headline>`。
  - 日期：同年 `MM-DD`，跨年 `YY-MM-DD`（标题里的年份是今天，跨年必须写年份，否则违反 G2）。
  - 对象简称：取对象段开头连续同类字符，最多 8 字（`bili账号`→`bili`、`用户级skill`→`用户级`）；不足 2 字取前 4 字。
  - 简称撞名：在**全部 active 键**范围内判断，撞了就改用完整对象段（≤12 字），不加序号。
  - **永远带对象**：唯一例外是 headline 里已含简称。宁可少显示一条（进 `fact_overflow`），也不显示认不出主体的行。
  - 超长（标签+headline >26 字）：不丢对象，照常渲染，记 `fact_label_long` 提示改短 headline。
  - 不放 id；`pinnedIds` 里保留全量。
- **静默丢条修复**：前 8 名里只要没渲染出来（`fitSection` 按字数挤掉、或总预算循环弹掉），一律写进 `fact_overflow`——以前只有「第 9 名以后」会被记录，挤掉的 3 条是静默蒸发的。
- **`fact_headline_missing`**：列出「已入选但没 headline」的键，推动补写。




### 15.8 坑类记忆的触发通道

问题：note 按设计永不进 L0，而 §6.6 的四个召回触发条件覆盖不到「报错怎么修」这类问法。实测 P09（B站抽帧证书错）三轮里败一轮——不是检索不到（那条 note 词法上排前 4 第 2），是模型压根没去检索。L0 尾注「更多细节用 mem_recall 查」太弱。

- **症状词**：内部 `kind=symptom` 事件，`refs` 恰好 1 条，`symptoms` 1–2 个（每个 2–8 字），`src` 允许 `agent`（新写入）或 `review`（补旧条目）。只写症状、不写修法；不进 `eventSearchText`、不参与打分、不单独成为召回条目。
- **新写入护栏**：仅限 `tags:["坑"]` 的 note；每会话最多 3 个；超限丢弃并给 warning，note 照常写。
- **L0 门铃行**（≤50 字，放在固定开销段）：

  `> 踩过 30 类坑（解析、注入、工具注册、凭据、证书）→ 报错/没反应/不出现先 mem_recall`

  - `N` 是 active 且有症状词的坑总数；
  - 括号里 3–5 个**类别词**，来自 `.dsh-mem/pit-categories.txt`（每行一个，缺省五个内置词）；
  - 超 50 字先砍类别词，不再罗列具体症状词；一条坑都没有时整行不渲染。
- **为什么是门铃不是目录**：2026-11-04 消融——A（120 字罗列 33 条症状词）23/24、B（完全无索引行）24/24、门铃 6/8。n=8 分不出高低，只能确认「无索引行不比有索引行差」。罗列症状词的维护成本不划算，改用门铃。
- **健康**：`pit_overflow`（没放下的类别词）、`pit_symptom_missing`（active 且带「坑」tag 但没有症状词/问法的条目）。
- **persona**：加【报错先查】——报错、怎么修、为什么不行这类问题，先 `mem_recall`；记忆里有现成修法就作为第一方案。
- **验收**：P09 从 6/9 提升到 **12/12**，且每轮都把 `-tls_verify 0` 作为第一方案。

### 15.9 坑类问法（doc2query）

症状词接召回时差 2 条没过门槛（基线 9/20、实验 11/20），但暴露了真问题：离线检索评测里**基线只有 9/20**，一半以上的真实问法词法上撞不到条目。

- **数据**：`kind=symptom` 事件加可选 `asks`（1–3 句，每句 6–40 字）；`mem_note` 加可选 `ask`。两者都没有 → `E_SYMPTOM_EMPTY`。
- **检索**：`symptomsInRecall`（默认 **true**）开启时，把该条目的 `symptoms` 与 `asks` 一并并入检索文本；关闭时与旧版逐字节一致。
- **评测（冻结协议，只跑一次）**：30 条留出查询，A 代理（见正文写现象）→ B 代理（见现象写问法），`asks` 由第三个模型从正文生成，三份输入的哈希在生成问法前落盘。
  - 结果：recall@5 **10/30 → 27/30**，b=18、c=1，单侧符号检验 p≈1.9e-5；
  - 回归：P01–P13 召回非空 11/12 不变；p95 24.5ms → 16.4ms；
  - 用词重合度分组：题面与对应 `asks` 的二词重合中位 **0.17**，仅 1 条 ≥0.30 —— 增益不是照抄措辞。
- **已知局限**：留出集是合成查询。从 359 个会话里挖出 216 条主人原话，**几乎都对不上坑类条目**（真人不说 `resourceBase`、`output` 这类词）——对真人问法的泛化**尚无证据**，需要真实查询攒够 20 条再按同一协议复测。

## 16. 2026-11-05 落地变更（与上文冲突时以本节为准）

0.2.2（commit `2d307ea`，tag `v0.2.2`）只动「观察与收尾」：指标口径、审计清单、回执存储，外加一个可写字段。召回打分、写入语义、L0 预算数字都没变。

### 16.1 坏行指标：当前值 + 历史峰值

旧实现用 `Math.max(health.corruptLines, n)` 累计，理由是「同一坏行每次重建都会被重新看见，不能虚增」。副作用是**只升不降**：坏行清掉之后干净重建实测 0 条，`health.json` 仍报 30，运维分不清「现在脏」和「曾经脏过」。

- `corruptLines` = 最近一次完整扫描（live + archive）**实际看到的坏行数**；坏行清掉后归零。
- 写入点从 `parseEventContent` 挪到 `rebuildState` 与 `appendEventToRoot`——一次扫描只落一次盘，而不是每次解析都写。
- `corruptLinesEver` = 历史峰值，单调不减。旧 `health.json` 没有该字段时，把旧 `corruptLines` 当作峰值迁入（否则升级后峰值凭空归零）。
- 读法：`corruptLines > 0` 才是当前有问题；`corruptLinesEver > 0` 只是「历史上脏过」。→ §4.5 §9.2

### 16.2 `rules_overflow` 只记真实损失，新增 `rules_near_limit`

§15.3 修的是「前缀漏算」这个算法错，但判定式里还留着一条：`fullRuleChars > 300` 也算 overflow。于是 6 条红线全部正常渲染、正文一个都没压，尾注照样喊「红线内容已截断」——指标和现场对不上，`rules_overflow` 失去了「需不需要召回全文」的指示意义。

- `rules_overflow` = 有红线被挤出前 6 条 **或** 任一条正文 > 32 字被压 **或** `rules_truncated_hard`。只有真损失才为真。
- `rules_near_limit` = 一行没丢、正文没压，但红线段名义宽度 > 300 字配额。只是提醒，注入内容一个字没少。
- 尾注四种说法：未常驻（另有 N 条，须召回）/ 已截断（内容不全，须召回）/ 接近配额（一行没丢，必要时召回）/ 正常（更多细节用 mem_recall 查）。
- 降级过程中两个标志会**重算**：两处硬截断各自调一次 `updateRuleFlags()`，尾注跟着重算，不会停在降级前那句话。→ §6.2 §6.3 §9.5

### 16.3 审计两条清单收紧

- **`suspected_should_be_fact`**：旧口径要求正文撞上**任意一个事实键的方面词**，于是「状态」「位置」这类高频词把一堆正常 note 拉进清单。现在与写入提醒 `factSmellWarnings` 共用同一个 `matchingKeys`：正文必须同时含某个键的**对象**和**方面**才算「像该键的新值」。宁可漏报，不要噪音。
- **`fadingEntries`**：旧口径只排除 `symptom`，于是 `close` / `retract` / `revise` / `supersede` / `alias` / `confirm` 这些**修正记录**也被算成「将被遗忘」——修正记录本来就不会被遗忘。改成白名单 `note / rule / decision / todo / fact`，事实按 `viewKind` 判定。→ §8.1 §9.2

### 16.4 召回回执瘦身

- 落盘每条只留得分前 5 的候选（`id` / `score` / `why` / `base`）+ `candidateCount`。完整候选是排序中间产物，审计用不到；`mem_audit(what="recall")` 照样能看到前 5 名和候选总数。
- 裁剪阈值 200 → **260**：原来每追加一条就把整个文件重写成 200 条，卡在上限的文件等于每次召回都整体重写一次；现在攒到 260 再裁回 200，重写摊薄到每 60 条一次。
- 别名挖掘跟着改：判「入选」看回执顶层 `picked`（不再依赖候选上的 `picked` 标记），`kind` 权重从 `state.byId` 反查。需要完整候选明细的调用方走 `recall(..., { onReceipt })` 拿内存版，落盘版不背这个责任。→ §9.1 §7.2

### 16.5 `src` 通道对模型开放

- `mem_fact` / `mem_note` 接受 `src: agent | user`（默认 `agent`）；写别的值直接 `E_SCHEMA`。`migrate:*` / `fold` / `review` 是内部来源，schema 认、模型不能自称。
- 起因：`src_user_ratio` / `src_user_count` 一直是 0——不是没人写 `src=user`，而是参数**根本没暴露**，等于字段写不进去。§13 第 9 条说的「没有强区分」实际上是连数据都没采到。
- 现在能写了，但**仍不参与评分**；要不要让 `src=user` 进 `w_imp`，还是开放问题。→ §3.1 §13
